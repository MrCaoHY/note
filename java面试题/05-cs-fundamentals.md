## 1. 计算机网络与协议栈（Q1 ~ Q17）

### Q1：OSI 七层模型与 TCP/IP 四层/五层模型各层职责与典型协议是什么？数据封装过程是怎样的？
- **直接结论**：
  - **OSI 七层模型**是理论标准（物、数、网、传、会、表、应）；**TCP/IP 四层模型**（网络接口层、网际层、传输层、应用层）是工程事实标准；教学与面试常折中为**五层模型**（物理层、数据链路层、网络层、传输层、应用层）。
- **底层原理与各层协议对比**：
  | OSI 七层 | TCP/IP 五层 | 核心职责与数据单元（PDU） | 典型协议 / 设备 |
  | :--- | :--- | :--- | :--- |
  | **应用层** | 应用层 | 为应用程序提供网络服务（报文 Message） | HTTP/HTTPS、DNS、FTP、SMTP、SSH、Dubbo |
  | **表示层** | 应用层 | 数据格式转换、加解密、压缩解压 | TLS/SSL、JSON/Protobuf、Base64 |
  | **会话层** | 应用层 | 建立、管理和终止会话（断点续传、Session） | RPC 会话控制、TLS 会话复用 |
  | **传输层** | 传输层 | **端到端（进程到进程）**数据传输与端口寻址（段 Segment / 数据报 Datagram） | **TCP、UDP**、QUIC |
  | **网络层** | 网络层 | **主机到主机**路径选择与逻辑寻址（分组 Packet） | **IP（IPv4/IPv6）**、ICMP（ping）、OSPF、路由器 |
  | **数据链路层** | 数据链路层 | 相邻节点间成帧传输、MAC 物理寻址、差错检测（帧 Frame） | Ethernet 以太网、**ARP**、PPP、交换机 |
  | **物理层** | 物理层 | 比特流光电信号转换与传输（Bit） | 双绞线、光纤、网卡、中继器 |
- **数据封装与解封装过程**：
  ```text
  应用层: [ HTTP Data ]
  传输层: [ TCP Header (Port) | HTTP Data ]
  网络层: [ IP Header (IP)    | TCP Header | HTTP Data ]
  链路层: [ MAC Header (MAC)  | IP Header  | TCP Header | HTTP Data | FCS 帧尾 ]
  物理层: 0101101010101... (电/光信号发送)
  ```
- **面试官连环追问**：
  1. **为什么有了 IP 地址还需要 MAC 地址？**
     - IP 地址是**逻辑地址**（决定最终目的地，路由转发用，类似收件人地址），会随所在网络变化；MAC 地址是**物理地址**（出厂烧录在网卡，决定下一跳是谁，类似快递员逐站交接）。IP 负责全局路由导航，MAC 负责局域网内点对点直达。
  2. **交换机和路由器的本质区别是什么？**
     - 二层交换机工作在**数据链路层**，根据 MAC 地址表转发数据帧，隔离冲突域但不隔离广播域；路由器工作在**网络层**，根据路由表和 IP 地址转发数据包，同时隔离冲突域和广播域。
- **实战避坑**：
  - 排查跨机房网络不通时，先 `ping`（ICMP 网络层）测连通性，再 `tcping` / `nc -zv`（传输层）测端口是否被防火墙或安全组拦截——能 `ping` 通不代表端口通，反之禁止 ICMP 的服务器 `ping` 不通但端口可以通。

### Q2：从输入 URL 到浏览器页面展示，全链路到底发生了什么？
- **直接结论**：
  - 经历 **URL 解析 → 缓存检查 → DNS 解析 → 建立 TCP 连接（及 TLS 握手）→ 发送 HTTP 请求 → 服务端网关/负载均衡/业务处理 → 响应返回与浏览器解析渲染 → TCP 断开或 Keep-Alive 复用** 八大阶段。
- **底层全链路流程图**：
  ```text
  浏览器输入 https://api.example.com/orders
     │
     ├─ 1. 检查浏览器强缓存 (Cache-Control / Expires)，命中则直接返回 (200 from cache)
     ├─ 2. DNS 解析: 浏览器缓存 -> OS缓存/hosts -> LocalDNS -> 根/顶级/权威DNS -> 获取 IP
     ├─ 3. 若接入 CDN，DNS CNAME 会导向智能调度 GSLB，返回距离最近的 CDN 边缘节点 IP
     ├─ 4. 构造数据包: 同网段直接 ARP 获取目标 MAC；跨网段 ARP 获取默认网关(路由器) MAC
     ├─ 5. TCP 三次握手 (SYN -> SYN+ACK -> ACK) 建立连接
     ├─ 6. HTTPS 发起 TLS 握手，校验 CA 证书并协商对称会话密钥
     ├─ 7. 发送 HTTP 请求报文 -> L4(LVS/F5)/L7(Nginx) 负载均衡 -> 网关鉴权限流 -> 后端微服务
     ├─ 8. 后端查询 Redis/MySQL 并返回 HTTP 响应 (如 200 OK / 304 Not Modified)
     └─ 9. 浏览器解析 HTML 构建 DOM 树 + CSS 构建 CSSOM 树 -> Render Tree -> Layout 布局 -> Paint 绘制
  ```
- **面试官连环追问**：
  1. **为什么浏览器会有同源策略？前端请求跨域时 URL 流程有什么变化？**
     - 浏览器在发送复杂跨域请求前会先发一次 `OPTIONS` **预检请求（Preflight）**，校验服务端返回的 `Access-Control-Allow-Origin`、`Access-Control-Allow-Methods` 等 CORS 响应头通过后，才发送真实请求。
  2. **浏览器对同一域名的并发 TCP 连接数有限制吗？**
     - HTTP/1.1 下 Chrome 对同一域名最多允许 **6 个并发 TCP 连接**（因此早期前端常做域名分片）；升级到 **HTTP/2** 后只需 **1 个 TCP 连接**即可多路复用并发传输。
- **实战避坑**：
  - 线上排查接口首包耗时高（TTFB 长），用 `curl -w "dns:%{time_namelookup} tcp:%{time_connect} tls:%{time_appconnect} ttfb:%{time_starttransfer} total:%{time_total}\n" -o /dev/null -s URL` 精准定位瓶颈究竟在 DNS、TCP、TLS 还是后端业务处理。

### Q3：DNS 域名解析完整流程是什么？递归查询与迭代查询的区别？HTTPDNS 是什么？
- **直接结论**：
  - 客户端向本地 DNS（LocalDNS）发起的是**递归查询**（LocalDNS 必须给最终结果）；LocalDNS 向根域名服务器、顶级域（TLD）、权威域名服务器发起的是**迭代查询**（对方只告诉你下一步找谁）。
- **底层原理**：
  - **查找顺序**：浏览器 DNS 缓存 → 操作系统缓存 → 本地 `hosts` 文件 → LocalDNS 服务器 → 根域名服务器（`.`）→ 顶级域名服务器（`.com`）→ 权威域名服务器（`example.com`）。
  - **DNS 传输协议**：常规查询使用 **UDP 53 端口**（速度快、无需握手、单包通常在 512 字节内）；当响应报文超过 512 字节（如 DNSSEC 或大量记录）或主从区域传送（AXFR）时回退到 **TCP 53 端口**。
- **面试官连环追问**：
  1. **什么是 DNS 劫持与污染？HTTPDNS 如何解决？**
     - 传统 DNS 基于明文 UDP 53 端口，易被运营商或中间人篡改返回广告 IP（劫持）或伪造错误 IP（污染），且 LocalDNS 缓存可能无视 TTL 导致切换流量不及时、跨网调度不准。
     - **HTTPDNS**：App/客户端绕过系统 LocalDNS，直接通过 **HTTP/HTTPS 请求（走 80/443 端口）** 访问云厂商提供的 HTTPDNS 服务器获取真实 IP，再直接向该 IP 建连（需配合 SNI 和 `Host` 请求头），彻底杜绝劫持并实现毫秒级精准调度。
- **实战避坑**：
  - JVM 默认会永久缓存成功的 DNS 解析结果（取决于安全策略，或默认 `networkaddress.cache.ttl`），当后端切流到阿里云 SLB 或修改域名解析 IP 时，Java 服务可能长期请求旧 IP。生产需检查 `$JAVA_HOME/jre/lib/security/java.security` 或通过 JVM 参数 `-Dsun.net.inetaddr.ttl=30` 缩短 DNS 缓存时间。

### Q4：ARP 协议原理与 CDN 加速工作原理是什么？
- **直接结论**：
  - **ARP（地址解析协议）**负责在局域网内将 **32 位 IPv4 地址解析为 48 位 MAC 物理地址**（同网段广播 ARP Request，单播 ARP Reply）；**CDN（内容分发网络）**通过智能 DNS 调度（GSLB）将用户请求路由至距离最近的边缘节点缓存服务器，减少回源和跨网延迟。
- **底层原理**：
  - **跨网段通信 MAC/IP 变化规律**：
    - 整个传输途中，**源 IP 和目的 IP 始终不变**（除非经过 NAT）。
    - 每经过一个路由器（三层转发），**源 MAC 和目的 MAC 都会改变**（改为当前出接口 MAC 和下一跳网关接口 MAC）。
  - **CDN 工作流程**：
    1. 配置域名 `img.shop.com` 为 `CNAME` 指向 CDN 厂商调度域名 `img.shop.com.cdn.dnsv1.com`。
    2. CDN 全局负载均衡（GSLB）根据请求者的 LocalDNS IP、运营商和节点健康度返回最优边缘节点 IP。
    3. 边缘节点命中缓存直接返回（Cache HIT）；未命中则逐级向上层节点或源站发起**回源请求**（Cache MISS），拉取后缓存在边缘节点并返回用户。
- **面试官连环追问**：
  1. **CDN 如何防止静态资源更新不生效？回源风暴怎么防？**
     - 资源 URL 带内容 Hash（如 `app.a1b2c3.js`）或版本号，永久缓存；若覆盖原文件需调用 CDN 刷新/预热 API。
     - **回源风暴防御**：边缘节点配置回源合并（Request Coalescing，同一 URL 并发未命中只放一个回源请求去源站），并开启预热（Warm-up）在大促前把热点资源提前推送到边缘节点。
- **实战避坑**：
  - 源站接入 CDN 后，后端直接取 `request.getRemoteAddr()` 拿到的是 CDN 回源节点的 IP 而非用户真实 IP，必须在网关/Nginx 解析 `X-Forwarded-For` 或 `True-Client-IP` 请求头（注意防范客户端伪造 `X-Forwarded-For`，只信任 CDN 可信网段传来的值）。

### Q5：TCP 和 UDP 的核心区别是什么？UDP 如何实现可靠传输？
- **直接结论**：
  - **TCP** 面向连接、可靠传输、面向字节流、支持流量与拥塞控制、首部开销 20~60 字节；**UDP** 无连接、尽最大努力交付、面向数据报文（有边界不粘包）、支持一对多/广播、首部固定 8 字节、无拥塞控制。
- **底层对比表**：
  | 对比维度 | TCP | UDP |
  | :--- | :--- | :--- |
  | **连接性** | 面向连接（一对一单播，3 次握手） | 无连接（支持一对一、一对多、多对多） |
  | **可靠性** | ACK 确认、超时重传、校验和、序号去重排序 | 仅提供可选校验和，不保证到达与顺序 |
  | **传输模式** | 面向**字节流**（无边界，有粘包/半包） | 面向**报文**（保留应用层边界，无粘包） |
  | **流量与拥塞控制** | 有滑动窗口与慢启动/拥塞避免 | 无（应用层发多少就发多少，易打满带宽） |
  | **典型应用** | HTTP/1.1/2、MySQL、Redis、Dubbo、SSH | DNS、DHCP、音视频直播、FPS 游戏、**QUIC (HTTP/3)** |
- **UDP 如何实现可靠传输？（如 QUIC / KCP 思路）**：
  - 在**应用层**重新实现 TCP 的可靠性机制，并针对特定场景做裁剪：
    1. **序列号 + ACK 确认 + 超时重传（ARQ）**：给每个 UDP 包编号，丢包重传。
    2. **选择性重传（SACK）或 FEC 前向纠错**：避免累积确认导致的无效重传；音视频场景可直接附带冗余纠错码免去重传延迟。
    3. **滑动窗口与拥塞控制**：避免发包过快撑爆接收方缓冲区或网络拥塞。
- **面试官连环追问**：
  1. **为什么音视频直播、实时竞技游戏和 HTTP/3 宁愿用 UDP 在应用层造轮子，也不用 TCP？**
     - TCP 的可靠性绑死了**严格按序交付**：一旦某个包丢失，内核缓冲区后续已经到达的包必须卡住等待重传（**TCP 队头阻塞**），导致几百毫秒卡顿；另外 TCP 握手与状态维护在弱网切换（4G 切 Wi-Fi）时连接直接中断。而基于 UDP（如 QUIC / KCP）可以做到连接迁移（Connection ID）与独立流控、不阻塞其他流。
- **实战避坑**：
  - UDP 发送单个数据包不要超过 MTU（以太网默认 1500 字节，减去 IP 头 20B 和 UDP 头 8B，有效载荷尽量控制在 **1472 字节以内**；公网安全建议 **<= 548 字节**），否则会在 IP 层分片，只要丢失任意一个分片整个 UDP 报文都会被丢弃。

### Q6：TCP 报文首部有哪些关键字段？为什么建立连接必须三次握手？
- **直接结论**：
  - TCP 首部固定 **20 字节**（含选项最长 60 字节），核心字段包括源/目的端口、32 位序列号（`seq`）、32 位确认号（`ack`）、控制位（`SYN`、`ACK`、`FIN`、`RST`、`PSH`、`URG`）、16 位窗口大小（`rwnd`）。
  - 三次握手的核心目的是：**同步双方的初始序列号（ISN）**、**确认双方收发能力均正常**、**阻止历史失效连接请求造成资源浪费**。
- **三次握手状态流转图**：
  ```text
  Client (CLOSED)                              Server (LISTEN)
     │                                             │
     │── SYN=1, seq=x ────────────────────────────▶│  Server 进入 SYN_RCVD
     │   (Client 进入 SYN_SENT)                     │  (放入半连接队列)
     │◀─ SYN=1, ACK=1, seq=y, ack=x+1 ─────────────│
     │                                             │
     │── ACK=1, seq=x+1, ack=y+1 ─────────────────▶│  Server 进入 ESTABLISHED
         (Client 进入 ESTABLISHED，可携带应用数据)       (移入全连接队列)
  ```
- **为什么不能是两次握手？（两大致命缺陷）**：
  1. **无法阻止历史失效连接的初始化**：假设客户端第一个 `SYN` 在网络中滞留，客户端超时重发并完成了一次正常通信且关闭连接；此时滞留的旧 `SYN` 终于抵达服务端。如果是两次握手，服务端回完 `SYN+ACK` 就直接进入 `ESTABLISHED` 并分配资源干等，客户端却直接丢弃该包（或发 `RST`），造成服务端大量死连接浪费内存。
  2. **无法确认客户端的接收能力及服务端 `ISN` 是否被收到**：第二次握手服务端把自己的初始序列号 `seq=y` 发给客户端，必须有第三次握手客户端回 `ACK(ack=y+1)`，服务端才能确认客户端收到了 `y` 并具备正常接收能力。
- **为什么不需要四次握手？**：
  - 因为服务端收到客户端 `SYN` 时处于 `LISTEN` 状态，没有未发送的数据，可以把对客户端的 `ACK` 和自己的 `SYN` **合并在同一个报文里发送**。
- **面试官连环追问**：
  1. **每次建立连接的初始序列号（ISN）为什么是随机递增的，而不是从 0 或 1 开始？**
     - 一是防止四元组复用时，旧连接的延迟报文被新连接误接收；二是防止攻击者轻易预测序列号，伪造报文实施 TCP 会话劫持（RST 攻击/数据注入）。
  2. **三次握手中第三次 ACK 丢失了会怎样？**
     - 服务端处于 `SYN_RCVD` 状态收不到第三次 `ACK`，会按指数退避重传 `SYN+ACK`（默认 `tcp_synack_retries=5`），期间客户端可能开始发数据包，该数据包携带了 `ACK` 标志位，服务端收到后也会直接转入 `ESTABLISHED`。
- **实战避坑**：
  - 抓包看到大量 `RST` 报文，常见原因：请求了未监听的端口、连接已关闭但对端继续发数据、服务端全连接队列满且开启 `tcp_abort_on_overflow=1`、或客户端硬关闭 `SO_LINGER(true, 0)`。

### Q7：什么是半连接队列与全连接队列？SYN Flood 攻击如何防御？
- **直接结论**：
  - Linux 内核为 TCP 握手维护两个队列：**半连接队列（SYN Queue）**存放收到 `SYN` 但未完成第三次握手的连接（`SYN_RCVD`）；**全连接队列（Accept Queue）**存放已完成三次握手等待应用进程 `accept()` 取走的连接（`ESTABLISHED`）。
- **底层原理与队列大小决定因素**：
  ```text
  Client SYN ─▶ [ 半连接队列 (SYN Queue) ] ─▶ 收到 Client ACK ─▶ [ 全连接队列 (Accept Queue) ] ─▶ 应用程序 accept()
                大小由 somaxconn、backlog、                         大小 = min(somaxconn, listen(backlog))
                tcp_max_syn_backlog 共同决定
  ```
  - **全连接队列溢出后果**：默认 `net.ipv4.tcp_abort_on_overflow = 0`，此时服务端直接**丢弃客户端的第三次 ACK**（假装没收到，触发客户端重传）；若设为 `1`，则直接给客户端回 `RST` 拒绝连接。高并发下 Tomcat/Nginx 若 `accept()` 不及时，全连接队列满会导致大量建连超时或 `Connection reset by peer`。
- **SYN Flood 攻击原理与防御**：
  - **攻击原理**：攻击者伪造大量不存在的源 IP 发送 `SYN` 包，服务端回复 `SYN+ACK` 永远等不到第三次 `ACK`，导致**半连接队列被占满**，正常用户无法建连。
  - **防御方案**：
    1. **开启 `SYN Cookies`（`net.ipv4.tcp_syncookies = 1`）**：半连接队列满时不再分配内存入队，而是根据四元组+时间戳+密钥算出一个加密值作为 `SYN+ACK` 的 `seq` 返回；收到第三次 `ACK` 时校验 `ack-1` 合法性再直接创建全连接，实现“零内存开销”防御。
    2. 调大 `tcp_max_syn_backlog` 与 `somaxconn`，调小 `tcp_synack_retries`（减少无效重传等待）。
    3. 接入云厂商高防 IP / WAF / eBPF XDP 在网卡驱动层直接过滤异常 SYN 包。
- **面试官连环追问**：
  1. **如何在线排查服务器是否发生了全连接队列溢出或半连接队列溢出？**
     - 使用 `ss -lnt` 查看监听端口的 `Recv-Q`（当前全连接队列已使用长度）和 `Send-Q`（全连接队列最大长度），若 `Recv-Q` 接近或等于 `Send-Q` 则说明溢出。
     - 使用 `netstat -s | grep -i listen` 查看 `times the listen queue of a socket overflowed`（全连接溢出计数）和 `SYNs to LISTEN sockets dropped`（半连接丢弃计数）。
- **实战避坑**：
  - Java `ServerSocket` 默认 `backlog` 是 `50`，Netty 默认参考系统的 `somaxconn`（Linux 旧版本默认仅 `128`，高并发压测务必调大 `/etc/sysctl.conf` 中的 `net.core.somaxconn = 4096` 或更高，并同步调大 Nginx/Tomcat `acceptCount`）。

### Q8：TCP 断开连接为什么需要四次挥手？为什么有 TIME_WAIT（2MSL）？
- **直接结论**：
  - TCP 是**全双工**通信，每个方向必须单独关闭：主动关闭方发 `FIN` 只代表它不再发送数据，但仍可接收被动方未发完的数据，因此被动方先回 `ACK`，等自己数据发完后再发 `FIN`，从而形成四次挥手。
  - 主动关闭方最后进入 `TIME_WAIT` 并等待 **2MSL**（Maximum Segment Lifetime，Linux 默认 1MSL = 30s，2MSL = **60 秒**），目的是**保证最后一个 ACK 能到达对端**以及**让本次连接的滞留报文在网络中完全消逝**。
- **四次挥手状态机**：
  ```text
  Client (主动关闭)                             Server (被动关闭)
     │                                             │
     │── FIN=1, seq=u ────────────────────────────▶│  Server 回复 ACK，进入 CLOSE_WAIT
     │   (Client 进入 FIN_WAIT_1)                   │  (Server 继续发送剩余数据...)
     │◀─ ACK=1, ack=u+1 ───────────────────────────│
     │   (Client 进入 FIN_WAIT_2)                   │
     │                                             │
     │◀─ FIN=1, ACK=1, seq=w, ack=u+1 ─────────────│  Server 发完数据调用 close()
     │                                             │  (Server 进入 LAST_ACK)
     │── ACK=1, seq=u+1, ack=w+1 ─────────────────▶│  Server 收到 ACK，进入 CLOSED
         (Client 进入 TIME_WAIT，等待 2MSL 后 CLOSED)
  ```
- **面试官连环追问**：
  1. **四次挥手一定必须是四次吗？有没有可能变成三次？**
     - 有可能！如果被动关闭方收到 `FIN` 时**刚好也没有数据要发送**，且开启了 TCP 延迟确认（Delayed ACK），服务端可以把对 `FIN` 的 `ACK` 和自己的 `FIN` **合并在一个报文中发送**，此时表现为三次挥手。
  2. **为什么是等待 2MSL，而不是 1MSL 或 3MSL？**
     - 去向最后一个 `ACK` 最多存活 1MSL；如果它丢失，被动方重传 `FIN` 到达主动方最多又需要 1MSL。一来一回正好 2MSL。超过 2MSL，两个方向上所有旧报文都已在网络中被路由器丢弃（TTL 归零）。
  3. **如果处于 `FIN_WAIT_2` 状态一直收不到对端 `FIN` 怎么办？**
     - 当使用 `shutdown(SHUT_WR)` 半关闭时可能停留在该状态；若是直接 `close()`，Linux 内核通过 `net.ipv4.tcp_fin_timeout`（默认 60s）兜底超时清理孤儿连接。
- **实战避坑**：
  - 切忌在不确定副作用时随意开启 `tcp_tw_recycle`（Linux 4.12 已被彻底移除），因为在 NAT 环境下多个客户端共享同一个公网 IP，时间戳不同步会导致服务端直接丢弃正常用户的 `SYN` 包造成随机建连失败。

### Q9：线上服务器出现大量 TIME_WAIT 或 CLOSE_WAIT 怎么排查与解决？
- **直接结论**：
  - **`TIME_WAIT` 过多**：发生在**主动关闭连接方**（常见于高并发短连接客户端、反向代理 Nginx、爬虫、压测机），会耗尽本地临时端口（`ip_local_port_range`）。解决核心是**改短连接为连接池长连接**与开启 `tcp_tw_reuse`。
  - **`CLOSE_WAIT` 过多**：发生在**被动关闭连接方**，说明收到了对端的 `FIN`，但**己方代码迟迟没有调用 `close()`**，100% 是**连接泄漏或线程阻塞 Bug**！
- **深度对比与排查方案**：
  | 异常状态 | 出现位置 | 根本原因 | 排查与解决措施 |
  | :--- | :--- | :--- | :--- |
  | **大量 `TIME_WAIT`** | **主动关闭方**（如调用下游微服务的网关、Nginx） | 高并发短连接频繁关闭；或服务端主动踢掉客户端 | 1. **开启 HTTP Keep-Alive / 连接池复用**（Nginx `upstream` 配置 `keepalive`；OkHttp/HttpClient 池化）<br>2. 开启内核复用参数 `net.ipv4.tcp_tw_reuse = 1`（仅对出向客户端连接生效）<br>3. 扩大端口范围 `net.ipv4.ip_local_port_range = 1024 65535` |
  | **大量 `CLOSE_WAIT`** | **被动关闭方**（如 Java 应用服务端或连接下游的客户端） | 对端已超时关闭，但我方代码**忘记在 `finally` 关闭流/连接**，或业务线程阻塞/死锁没走到 `close()` | 1. `ss -antp \| grep CLOSE-WAIT` 找到对应进程 PID 与连接目标<br>2. `jstack <pid>` 查看线程堆栈是否卡在某外部接口调用或死锁<br>3. 检查 HttpClient/Redis/JDBC 是否未释放连接（如未关闭 `CloseableHttpResponse` 的实体流） |
- **面试官连环追问**：
  1. **为什么 HttpClient 使用时忘了消费 `EntityUtils.consume()` 或关闭 `Response` 会导致 `CLOSE_WAIT`？**
     - 当服务端因空闲超时主动发 `FIN` 关闭连接时，客户端连接还躺在连接池里或未归还，如果没有定期清理过期/空闲连接线程（IdleConnectionEvictor），该 Socket 会长期停留在 `CLOSE_WAIT` 状态直到端口或句柄耗尽（`Too many open files`）。
- **实战避坑**：
  - 生产环境查看所有 TCP 状态统计的一行神器命令：
    `ss -ant | awk 'NR>1 {++S[$1]} END {for(a in S) print a, S[a]}'`

### Q10：TCP 是如何保证可靠传输的？（ARQ、滑动窗口、流量控制、SACK）
- **直接结论**：
  - TCP 通过**校验和、序列号与确认应答（ACK）、超时重传（ARQ）、滑动窗口（流量控制）、拥塞控制**五大机制协同实现可靠传输。
- **核心机制拆解**：
  1. **停止等待 ARQ vs 连续 ARQ（滑动窗口）**：
     - 停止等待每发一个包就等 ACK，链路利用率极低；**滑动窗口**允许发送方在未收到 ACK 前连续发送窗口大小 `W` 内的数据，窗口随着收到 ACK 向右滑动。
  2. **流量控制（Flow Control）**：
     - 接收方在每次返回的 TCP 首部 `Window` 字段通告自己当前剩余接收缓冲区大小（**`rwnd`**），发送方发送窗口不能超过 `rwnd`，防止发送太快打满接收端缓冲区造成丢包。
     - **零窗口死锁防范**：当接收方通告 `rwnd=0` 后，发送方停止发数据并启动**持续计时器（Persistence Timer）**，超时发送 `ZWP`（Zero Window Probe）零窗口探测报文询问最新窗口大小。
  3. **超时重传（RTO）与 SACK（选择性确认）**：
     - RTO（Retransmission Timeout）根据 RTT（往返时间）动态加权平滑计算，且每次重传发生**指数退避**（RTO 翻倍）。
     - 普通累积确认下，若包 1,2,4,5 到达而 3 丢失，接收方只能不断回 `ACK=3`，发送方不知 4,5 已收到。开启 **SACK** 后，TCP Options 会携带已收到的乱序块边界（如 `SACK 4-5`），发送方只需精确重传包 3。
- **面试官连环追问**：
  1. **什么是 Nagle 算法与延迟确认（Delayed ACK）冲突导致的 40ms/200ms 延迟坑？**
     - **Nagle 算法**：为了减少小包数量，若还有未确认的数据，禁止发送不足 MSS 的小包（攒够 MSS 或等上一个 ACK 到来才发）。
     - **延迟 ACK**：接收方收到数据不立即回 ACK，而是等最多 40ms（Linux）看有没有顺带要发的数据一起捎带确认。
     - **叠加灾难**：当发送方连续执行两次小 `write()`（如写 HTTP Header 再写 Body），第一包发出等 ACK，第二包被 Nagle 扣住，接收方等满 40ms 才回第一包的 ACK，每次请求凭空多出 40ms 延迟！**解决**：高性能 RPC/Netty 默认设置 **`TCP_NODELAY = true`** 禁用 Nagle 算法。
- **实战避坑**：
  - 高并发吞吐调优不仅看应用代码，还要看内核缓冲区 `net.ipv4.tcp_rmem` 和 `tcp_wmem`（若窗口过大在长肥管道 BDP 场景下限制吞吐，需开启 `tcp_window_scaling = 1`）。

### Q11：详细阐述 TCP 的拥塞控制机制：慢开始、拥塞避免、快重传、快恢复及 BBR？
- **直接结论**：
  - 流量控制针对**点对点接收能力**（`rwnd`），而拥塞控制针对**整个网络链路的承载能力**（维护拥塞窗口 **`cwnd`**），发送方实际发送窗口取 **`min(cwnd, rwnd)`**。经典拥塞控制由**慢开始、拥塞避免、快重传、快恢复**四步组成。
- **经典 Reno 算法四步曲线**：
  ```text
  cwnd
   ▲
   │            ╱ 拥塞避免 (+1/RTT)
   │           ╱ ╲ (发生超时重传: ssthresh=cwnd/2, cwnd=1)
   │          ╱   ╲
   │  ssthresh     ╲       ╱ 收到 3 个冗余 ACK (快恢复: ssthresh=cwnd/2, cwnd=ssthresh)
   │    ─ ─ ─╱─ ─ ─ ╲─ ─ ─╱─ ─ ─
   │        ╱        ╲
   │       ╱ 慢开始   ╲
   │      ╱ (指数×2)   ╲ (重新慢开始)
   └─────┴──────────────┴──────────────▶ 轮次 (RTT)
  ```
  1. **慢开始（Slow Start）**：初始 `cwnd`（现代 Linux 默认 `10 * MSS`），每收到一个 ACK，`cwnd` 加 1，即**每个 RTT 翻倍（指数增长）**，直到达到慢开始门限 `ssthresh`。
  2. **拥塞避免（Congestion Avoidance）**：`cwnd >= ssthresh` 后，每个 RTT 仅线性 **`+1`（加法增大）**。
  3. **快重传（Fast Retransmit）**：接收方收到失序报文时立即重复发送前一个已确认序号的 ACK；发送方**连续收到 3 个相同的冗余 ACK**，无需等 RTO 超时，直接重传丢失报文段。
  4. **快恢复（Fast Recovery）**：触发快重传时，说明网络还能收到后续包、只是轻微拥塞，因此把 `ssthresh` 设为当前 `cwnd / 2`，同时 **`cwnd` 直接设为新的 `ssthresh`**（而不是跌回 1），随后直接进入拥塞避免阶段。*(若是 RTO 超时重传，则说明严重拥塞，`cwnd` 狠心跌回 1 重新慢开始)*。
- **面试官连环追问**：
  1. **传统基于丢包的拥塞控制（CUBIC/Reno）有什么缺点？Google BBR 算法核心思想是什么？**
     - 传统算法只有在“丢包”时才降速，这在路由器大缓存（Bufferbloat 缓冲区膨胀）下会导致高延迟，而在高丢包无线弱网下又会误判拥塞导致带宽暴跌。
     - **BBR（Bottleneck Bandwidth and RTT）**：不再以丢包作为拥塞信号，而是实时测量链路上的**最大带宽（BtlBw）**和**最小往返延迟（RTprop）**，将发送速率精准控制在 `BtlBw × RTprop` 的最优甜点上，在有一定丢包率的跨国/弱网环境下吞吐量可提升数倍。
- **实战避坑**：
  - 线上长连接如果空闲一段时间后突然发送大报文，默认 `net.ipv4.tcp_slow_start_after_idle = 1` 会让 `cwnd` 退化回初始值重新慢开始，影响突发性响应延迟，高并发服务可考虑关闭该参数（设为 `0`）。

### Q12：什么是 TCP 粘包和拆包？为什么 UDP 没有粘包？如何解决？
- **直接结论**：
  - TCP 是**面向字节流**的无边界协议，操作系统会根据缓冲区大小和 MSS 自动合并或拆分应用层写入的字节流，导致接收端一次 `read()` 可能读到半个包（**拆包/半包**）或多个包连在一起（**粘包**）。
  - UDP **面向报文**，内核保留每条消息的完整边界，一次 `recvfrom()` 对应发送端一次 `sendto()`，因此不存在粘包。
- **产生根本原因**：
  1. 发送端写入字节大于 Socket 发送缓冲区，或大于 MSS（默认 1460B），在传输层被拆分发送（拆包）。
  2. 发送端开启 Nagle 算法，或连续小包在接收端来不及读走，在内核接收缓冲区中排在一起（粘包）。
- **应用层四大经典解决方案（对应 Netty 解码器）**：
  1. **固定长度包**：不足补齐（如定长 128 字节）→ Netty `FixedLengthFrameDecoder`。
  2. **特殊分隔符**：包尾追加 `\r\n` 或 `$_$` → Netty `DelimiterBasedFrameDecoder` / `LineBasedFrameDecoder`（HTTP 请求头、Redis RESP 协议采用）。
  3. **消息头 + 消息体（最通用、工业级首选）**：消息头固定 4 字节声明消息体长度 `Length`，接收端先读 4 字节再精确读取 `Length` 字节 → Netty **`LengthFieldBasedFrameDecoder`**（Dubbo、RocketMQ、自定义 RPC 协议均采用）。
  4. **短连接**：每次发完一个包就关闭连接（性能极差，不推荐）。
- **面试官连环追问**：
  1. **用 `LengthFieldBasedFrameDecoder` 时如果遇到恶意攻击者发来一个 `Length = 2GB` 的假包头怎么办？**
     - 必须在构造 `LengthFieldBasedFrameDecoder` 时设置合理的 **`maxFrameLength`**（如 10MB），超过直接抛出 `TooLongFrameException` 并关闭连接，防止触发 OOM。
- **实战避坑**：
  - 严禁在面试中说“TCP 协议自己会处理粘包”——严格来说“粘包”是伪命题，TCP 只管按序交付字节流，**识别消息边界永远是应用层协议的职责**。

### Q13：HTTP/1.0、HTTP/1.1、HTTP/2.0、HTTP/3.0（QUIC）核心演进与区别是什么？
- **直接结论**：
  - HTTP/1.0 每次请求新建 TCP 连接；HTTP/1.1 引入**长连接（Keep-Alive）与管道化**，但存在**应用层队头阻塞**；HTTP/2.0 引入**二进制分帧、多路复用、头部压缩 HPACK、服务器推送**，彻底消除 HTTP 队头阻塞，但仍受限于 **TCP 传输层队头阻塞**；HTTP/3.0 底层改用基于 **UDP 的 QUIC 协议**，彻底消除传输层队头阻塞并支持 0-RTT 与连接迁移。
- **四代版本核心对比表**：
  | 对比维度 | HTTP/1.0 | HTTP/1.1 | HTTP/2.0 | HTTP/3.0 (QUIC) |
  | :--- | :--- | :--- | :--- | :--- |
  | **传输协议** | TCP（短连接） | TCP（默认长连接 `Keep-Alive`） | TCP（单连接多路复用） | **UDP + QUIC** |
  | **数据格式** | 纯文本 | 纯文本 | **二进制分帧**（Frame + Stream） | 二进制分帧（原生内置 TLS 1.3） |
  | **队头阻塞** | 每次新开连接 | 存在（Pipeline 必须按请求顺序响应） | HTTP 层消除；**仍存在 TCP 层队头阻塞** | **彻底消除**（各 Stream 独立丢包重传） |
  | **头部压缩** | 无 | 无（每次带冗余 Cookie/UA） | **HPACK**（静态/动态表+Huffman） | **QPACK**（避免动态表乱序依赖阻塞） |
  | **连接迁移** | 不支持 | 不支持 | 不支持（切网换 IP 就断连） | **支持**（基于 64 位 Connection ID） |
- **面试官连环追问**：
  1. **为什么说 HTTP/2 在弱网丢包环境下性能反而可能不如多个并发的 HTTP/1.1 连接？**
     - HTTP/2 把所有请求复用在 **1 条 TCP 连接**上。一旦该连接发生 1 个 TCP 包丢失，整个连接上的所有并发 Stream 都要在内核里阻塞等待重传；而 HTTP/1.1 通常有 6 条独立 TCP 连接，一条丢包不影响另外 5 条。这正是推动 HTTP/3（QUIC）诞生的核心原因。
- **实战避坑**：
  - 使用 Nginx 开启 HTTP/2 时注意：**Nginx 与上游后端（Tomcat/Spring Boot）之间默认仍通过 HTTP/1.1 通信**，因为内网延迟极低，无需为了多路复用增加解析复杂度；而在 `Nginx <-> 客户端` 边缘侧强烈建议开启 `listen 443 ssl http2;`。

### Q14：常见 HTTP 状态码有哪些？GET 与 POST 的本质区别与幂等性？
- **直接结论**：
  - 状态码按首位数字分类：`1xx` 信息提示、`2xx` 成功、`3xx` 重定向、`4xx` 客户端错误、`5xx` 服务端错误。
  - GET 与 POST 本质上底层都是基于 TCP 发送文本报文，区别在于 **HTTP 语义规范与幂等性**：GET 用于获取资源（安全且幂等，可被浏览器缓存），POST 用于提交/创建资源（非安全、非幂等）。
- **高频状态码速查**：
  - `200 OK` / `204 No Content`（成功无响应体，常用于 DELETE 或 OPTIONS） / `206 Partial Content`（断点续传 Range 请求）。
  - `301 Moved Permanently`（永久重定向，搜索引擎更新链接，浏览器缓存） vs **`302 Found`**（临时重定向，可能把 POST 转为 GET） vs `307/308`（严格保留原请求方法不变的临时/永久重定向）。
  - `304 Not Modified`（协商缓存命中，ETag / Last-Modified 未变化）。
  - `400 Bad Request`（参数格式/校验错误） / **`401 Unauthorized`**（未认证/Token 失效） / **`403 Forbidden`**（已认证但无权限访问） / `404 Not Found` / `405 Method Not Allowed` / `429 Too Many Requests`（限流触发）。
  - `500 Internal Server Error`（后端未捕获异常） / **`502 Bad Gateway`**（网关收到上游无效响应或后端进程挂了） / `503 Service Unavailable`（服务过载/熔断/维护） / **`504 Gateway Timeout`**（网关等待上游后端响应超时）。
- **GET vs POST 深入对比**：
  - **幂等性（Idempotency）**：执行一次和执行 N 次对系统资源产生的影响完全相同。`GET`、`HEAD`、`PUT`、`DELETE` 从 RESTful 语义上应设计为幂等，`POST` 非幂等。
  - **数据包次数误区**：网传“GET 发 1 个包，POST 发 2 个包（先发 Header 回 100-continue 再发 Body）”**并非绝对**——仅当请求体较大或显式携带 `Expect: 100-continue` 头时某些客户端才分两次发，常规小 POST 请求在现代浏览器和 HttpClient 中也是合并一次发出的。
  - **安全性与长度限制**：URL 长度限制并非 HTTP 协议规定，而是浏览器（如 IE 2KB、Chrome ~8KB）和 Web 服务器（Nginx `large_client_header_buffers`）的限制。
- **面试官连环追问**：
  1. **线上网关（如 Nginx）频繁报 `502` 和 `504` 如何一眼区分排查方向？**
     - **`502 Bad Gateway`**：重点查后端服务是否宕机、端口未启动、进程 OOM 被杀、或者后端主动断开了连接（如 Keep-Alive 超时时间短于 Nginx）。
     - **`504 Gateway Timeout`**：后端活着但**处理太慢**，超过了 Nginx 的 `proxy_read_timeout`（默认 60s），重点查慢 SQL、死锁、下游接口卡死或线程池耗尽。
- **实战避坑**：
  - **永远不要用 GET 请求执行写操作（如删数据/转账）**，否则一旦被搜索引擎爬虫预抓或浏览器预加载命中，会直接触发线上数据篡改事故，且极易遭受 CSRF 攻击。

### Q15：Cookie、Session、Token（JWT）的区别与演进是什么？分布式 Session 怎么解决？
- **直接结论**：
  - **Cookie** 存在客户端，大小限 4KB，每次请求同域自动携带；**Session** 存在服务端（内存/Redis），通过 Cookie 中的 `JSESSIONID` 映射状态；**Token（如 JWT）**由服务端签名后交由客户端保存并放在 `Authorization` 请求头中，服务端**无状态验证签名即可**，天然适应分布式与跨端（App/小程序）。
- **核心对比表**：
  | 维度 | Cookie + Session | Token (JWT) |
  | :--- | :--- | :--- |
  | **存储位置** | Session 数据在服务端，Cookie 仅存 `SessionId` | 全量状态（Payload）经 Base64 编码后存在客户端 |
  | **扩展性** | 集群需做 Session 共享，有存储压力 | **无状态**，任意节点用密钥验签即可，横向扩展极易 |
  | **安全性** | 易受 **CSRF** 攻击（浏览器自动带 Cookie） | 不依赖 Cookie，天然免疫常规 CSRF；但防 **XSS** 窃取 |
  | **主动注销能力** | **极强**（服务端删 Redis Key 立即踢下线） | **较弱**（签发后未过期前一直有效，需借助黑名单弥补） |
- **分布式环境下 Session 共享四大方案**：
  1. **集中式存储（最推荐）**：Session 存入 **Redis**（如引入 `spring-session-data-redis`），所有节点统一读写 Redis。
  2. **Nginx IP Hash 粘性会话**：同一 IP 路由到同一台机器（节点宕机则会话全丢，且 NAT 下易流量倾斜，不推荐）。
  3. **Token 无状态替代**：直接放弃传统 Session，全面转向 JWT + Refresh Token。
- **面试官连环追问**：
  1. **JWT 是加密的吗？里面能放敏感信息吗？如何实现“踢人下线”和“自动续期”？**
     - JWT 由 `Header.Payload.Signature` 三部分组成，前两部分只是 **Base64URL 编码**（明文可解！），只有第三部分是 HMAC/RSA 签名，防篡改但不防窃听，**绝对不能放密码、身份证等敏感信息**。
     - **踢人下线**：改密码/封号时将 `jti`（Token ID）或用户版本时间戳存入 Redis 黑名单，或采用双 Token 机制（短效 AccessToken 15 分钟 + 长效 RefreshToken 7 天存 Redis），退出或踢人时删除 Redis 中的 RefreshToken。
- **实战避坑**：
  - Cookie 防护必加三大属性：`HttpOnly`（防 JS `document.cookie` 读取防 XSS）、`Secure`（仅 HTTPS 传输）、`SameSite=Lax/Strict`（防 CSRF）。

### Q16：HTTPS 是如何保证安全性的？TLS 1.2 与 TLS 1.3 握手过程有何区别？
- **直接结论**：
  - HTTPS = **HTTP + TLS**，利用 **非对称加密（安全协商密钥） + 对称加密（高效加密业务数据） + 摘要与数字签名（防篡改与防中间人）** 实现机密性、完整性和身份认证。
  - **TLS 1.2** 需要 **2-RTT** 完成完整握手；**TLS 1.3** 精简了交互且强制采用前向安全算法（ECDHE），将握手压缩至 **1-RTT**，并支持会话恢复下的 **0-RTT**。
- **TLS 1.2 vs TLS 1.3 握手对比流程**：
  ```text
  【TLS 1.2 (2-RTT)】
  1. Client -> Server: ClientHello (TLS版本, 加密套件, 随机数 R1)
  2. Server -> Client: ServerHello (选定套件, 随机数 R2) + Certificate (CA数字证书) + ServerHelloDone
  3. Client 校验证书链 -> 生成 Pre-Master Secret 用证书公钥加密发送 (ClientKeyExchange)
     -> ChangeCipherSpec -> Finished (用主密钥摘要校验)
  4. Server 用私钥解密得 Pre-Master -> 生成 Master Secret -> ChangeCipherSpec -> Finished
  (注：若使用 ECDHE 密钥交换，Server 第 2 步多发 ServerKeyExchange 携带临时椭圆曲线公钥)

  【TLS 1.3 (1-RTT)】
  1. Client -> Server: ClientHello (直接预猜 Server 会选 ECDHE，把客户端公钥 KeyShare 直接带过去!)
  2. Server -> Client: ServerHello + 选定 KeyShare + 证书 + Finished (Server 此时已算出对称密钥，第2步后半段已经加密!)
  3. Client 验签证书 + 算出对称密钥 -> Finished + 直接开始发送加密后的 HTTP 请求!
  ```
- **CA 数字证书防中间人攻击验证链**：
  1. 服务端向权威 CA 机构提交域名和公钥；CA 用自己的**私钥**对“服务端信息 + 公钥”的哈希值签名，生成数字证书。
  2. 浏览器/操作系统出厂内置了受信任的**根 CA 公钥**。
  3. 收到证书后，客户端用内置 CA 公钥逐级向下验签：一致说明公钥确属该域名且未被篡改；再校验域名匹配、证书有效期及 CRL/OCSP 吊销状态。
- **面试官连环追问**：
  1. **什么是前向安全性（Forward Secrecy）？为什么 TLS 1.3 废弃了 RSA 密钥交换？**
     - 如果用静态 RSA 私钥直接解密 Pre-Master Secret，一旦未来某天黑客窃取了服务器私钥，就能把过去截获的所有历史加密流量全部解密！
     - **ECDHE** 每次握手都在内存里**临时随机生成一对椭圆曲线公私钥**，握手完立刻销毁，即使未来服务器主私钥泄露，历史流量依然无法被破解。
- **实战避坑**：
  - 线上 TLS 证书过期是 P0 级高频故障，务必通过 Prometheus `blackbox_exporter` 或云监控配置证书有效期小于 30 天告警。

### Q17：WebSocket 的工作原理是什么？与 HTTP 长轮询、SSE 有何区别？
- **直接结论**：
  - **WebSocket** 是基于 TCP 的**全双工应用层通信协议**，通过一次 **HTTP Upgrade 握手**将连接升级为永久双向长连接，之后客户端与服务端可随时主动互推二进制或文本帧。
- **核心原理与选型对比**：
  - **握手报文**：客户端发 `GET /ws HTTP/1.1` 并带 `Upgrade: websocket`、`Connection: Upgrade`、`Sec-WebSocket-Key`；服务端返回 **`101 Switching Protocols`** 和计算后的 `Sec-WebSocket-Accept`。
  - **技术选型对比**：
    | 方案 | 通信方向 | 底层协议 | 适用场景 |
    | :--- | :--- | :--- | :--- |
    | **短轮询 / 长轮询 (Long Polling)** | 单向伪推送（客户端不断发 HTTP） | HTTP | 简单扫码登录状态检测、Nacos 配置监听（30s 长轮询） |
    | **SSE (Server-Sent Events)** | **服务端单向推客户端** | 纯 HTTP（`text/event-stream`） | **AI 大模型流式打字输出（ChatGPT）**、股票行情单向推送（自带断线重连） |
    | **WebSocket** | **真正全双工双向** | 独立二进制帧协议（ws/wss） | 在线聊天 IM、协同编辑、网页端实时游戏、高频弹幕 |
- **面试官连环追问**：
  1. **WebSocket 如何实现心跳保活与集群状态路由？**
     - 协议层原生支持 `Ping (0x9)` / `Pong (0xA)` 控制帧，应用层通常结合 Netty `IdleStateHandler` 定时发送业务心跳包，超时连续几次未响应则断开清理通道释放内存。
     - 集群部署时，用户 A 连在节点 1、用户 B 连在节点 2，需在 Redis 维护 `userId -> nodeAddr` 路由表，通过 MQ 广播或 RPC 定向转发消息给对应节点推送。
- **实战避坑**：
  - Nginx 代理 WebSocket 默认 **60 秒无数据交互会切断连接**（`proxy_read_timeout 60s`），必须显式配置 `proxy_http_version 1.1;`、`Upgrade` 头传递及合理的心跳间隔（如每 25 秒发一次 Ping）。

## 2. 操作系统与 Linux 实战排查（Q18 ~ Q30）

### Q18：进程、线程、协程（及 Java 21 虚拟线程）的本质区别是什么？上下文切换切换哪些内容？
- **直接结论**：
  - **进程**是操作系统**资源分配**的基本单位（拥有独立虚拟地址空间、页表、文件描述符表）；**线程**是 **CPU 调度**的基本单位（共享进程堆与方法区，私有栈与程序计数器）；**协程**是**用户态轻量级线程**（如 Go goroutine、Java 21 `VirtualThread`），由语言运行时/JVM 调度而非 OS 内核，切换极快且可支撑百万级并发。
- **核心对比表**：
  | 对比维度 | 进程 (Process) | 内核线程 (OS Thread) | 协程 / 虚拟线程 (Coroutine / VirtualThread) |
  | :--- | :--- | :--- | :--- |
  | **调度主体** | 操作系统内核 | 操作系统内核 | **用户态运行时 / JVM**（M:N 挂载到载体线程） |
  | **资源隔离** | 独立虚拟内存、FD 表、安全上下文 | 共享进程内存与 FD，私有栈（默认约 1MB） | 共享进程内存，轻量动态栈（KB 级，用时按需扩缩） |
  | **切换开销** | 极高（切换页表 CR3、刷新 TLB、CPU 缓存失效 + 内核态上下文） | 较高（需陷入内核态保存寄存器、PC、栈指针，约微秒级） | **极低**（纯用户态保存少量寄存器与栈帧，纳秒级） |
  | **通信与健壮性** | 需 IPC 通信；单进程崩溃不影响其他进程 | 共享内存直接通信但需锁；单线程未捕获异常可能拖垮整个进程 | 通过 Channel / 队列或共享内存；遇到阻塞自动让出（unmount）载体线程 |
- **面试官连环追问**：
  1. **Java 21 虚拟线程遇到 `synchronized` 阻塞会怎样？（Pinning 钉住问题）**
     - 在 Java 21 中，如果虚拟线程在 `synchronized` 代码块内部执行阻塞 IO（或调用 JNI），它会把底层的 OS 载体线程（Carrier Thread）**钉住（Pin）**而无法让出，高并发下可能拖垮载体线程池；因此高并发虚拟线程下建议使用 `ReentrantLock` 替代 `synchronized`（注：Java 24 JEP 491 已解决 `synchronized` pinning）。
- **实战避坑**：
  - 线上不要盲目调大业务线程池到几千个 OS 线程：每个线程默认栈占 1MB 堆外内存，2000 个线程光栈内存就吃掉 2GB，且频繁上下文切换（`vmstat` 中 `cs` 飙高）反而让吞吐量暴跌。

### Q19：进程间通信（IPC）有哪些方式？各自优缺点与适用场景？
- **直接结论**：
  - Linux 经典 6 大 IPC 方式：**管道（匿名管道/命名管道 FIFO）、消息队列（POSIX/System V）、共享内存、信号量、信号（Signal）、Socket（含 Unix Domain Socket）**。
- **六大 IPC 机制核心对比**：
  | IPC 方式 | 原理与特点 | 速度 / 缺点 | 典型应用 |
  | :--- | :--- | :--- | :--- |
  | **匿名管道 (Pipe)** | 内核缓冲区实现的**半双工**字节流 | 仅限**父子/兄弟亲缘进程**；数据读完即销毁 | Shell 管道命令 `ps -ef \| grep java` |
  | **命名管道 (FIFO)** | 文件系统中存在的特殊管道文件 | 支持无亲缘进程；仍受限于单机半双工与缓冲区大小 | 轻量级本地日志流传递 |
  | **消息队列** | 内核链表存储带类型的格式化消息 | 无需读写同步等待；但存在**两次用户态-内核态拷贝** | 传统异步解耦（现代多用 Kafka/RabbitMQ 替代） |
  | **共享内存 (Shared Memory)** | 多个进程把**同一块物理内存**映射到各自虚拟地址空间 | **速度最快（零拷贝）**；但**不提供同步机制**，必须配合信号量或互斥锁 | 高频交易行情共享、音视频帧共享、`/dev/shm` |
  | **信号量 (Semaphore)** | 本质是内核计数器，实现进程间互斥与同步 | 不传业务数据，仅用于控制共享资源访问权限 | 配合共享内存实现 P/V 原语同步 |
  | **信号 (Signal)** | 异步通知机制（软件中断） | 只能传递信号编号，无法传复杂数据 | `kill -15` (SIGTERM 优雅停机)、`kill -9` (SIGKILL 强杀) |
  | **Socket / Unix Domain Socket** | 通用流/报文通信（UDS 不走网卡和 TCP/IP 协议栈） | 最通用，支持跨主机；UDS 本地比 TCP 回环快约 30%+ | Docker Daemon (`/var/run/docker.sock`)、Nginx 与 PHP-FPM |
- **面试官连环追问**：
  1. **为什么 Docker 和本地 MySQL 客户端连接首选 Unix Domain Socket 而不是 `127.0.0.1` TCP？**
     - 本地 TCP 回环仍要走完整的传输层与网络层协议栈封装、校验和计算及路由表查找；而 Unix Domain Socket 直接在内核缓冲区进行内存拷贝，绕过协议栈，延迟更低、吞吐更高。
- **实战避坑**：
  - Spring Boot 优雅停机依赖 `kill -15 <pid>`（发送 `SIGTERM`），**绝对禁止在日常发布脚本中直接 `kill -9`**（`SIGKILL` 无法被 JVM 捕获，会直接掐断正在处理中的事务、MQ 消费确认与数据库写入）。

### Q20：线程同步的常见机制有哪些？用户态锁与内核态锁的区别？
- **直接结论**：
  - 常见线程同步机制：**互斥锁（Mutex）、自旋锁（Spinlock）、读写锁（RWLock）、条件变量（Condition Variable）、信号量（Semaphore）、屏障（Barrier）**。
  - 核心差异在于**获取不到锁时的等待策略**：用户态自旋锁通过 CPU 空转 CAS 重试避免上下文切换；内核态互斥锁会挂起线程并让出 CPU，等待唤醒时产生两次上下文切换。
- **对比与选型逻辑**：
  1. **互斥锁（Mutex）**：加锁失败线程进入休眠（内核态切换开销约微秒级），适合**临界区执行时间较长**（如含 IO、复杂计算）的场景。
  2. **自旋锁（Spinlock）**：加锁失败线程在用户态 `while` 循环 CAS 忙等，**不释放 CPU**。适合**临界区极短**（几十纳秒）且多核 CPU 环境，否则会空耗 CPU 100%。
  3. **读写锁（Read-Write Lock）**：读读共享、读写互斥、写写互斥，适合**读多写少**场景（需注意写饥饿问题，如 Java `StampedLock` 乐观读进一步提升并发）。
  4. **条件变量（Condition）**：必须与互斥锁配合使用，当条件不满足时原子性地释放锁并挂起等待通知（对应 Java `Lock.newCondition()` 与 `Object.wait/notify`）。
- **面试官连环追问**：
  1. **既然用户态自旋快，为什么不全部用自旋锁？单核 CPU 能用自旋锁吗？**
     - 临界区很长或发生 IO 阻塞时，自旋会白白烧干整颗 CPU 核心，不如挂起让其他就绪线程运行；**单核 CPU 非抢占式内核下绝对不能使用纯粹的自旋锁**，因为持有锁的线程无法获得 CPU 时间片执行释放，自旋线程会直接死锁卡死。
- **实战避坑**：
  - Java `synchronized` 本质上是**先用户态自旋（自适应自旋轻量锁）→ 膨胀为内核态 `ObjectMonitor` 互斥锁（重量级锁）**的混合体，兼顾了短临界区低延迟与长临界区不浪费 CPU 的优势。

### Q21：操作系统常见的 CPU 调度算法有哪些？Linux 默认用什么调度器？
- **直接结论**：
  - 常见 CPU 调度算法：**先来先服务（FCFS）、短作业优先（SJF）、优先级调度、时间片轮转（RR）、多级反馈队列（MLFQ）**。现代 Linux 通用桌面与服务器默认采用 **CFS（Completely Fair Scheduler，完全公平调度器）**（Linux 6.6+ 引入基于虚拟截止时间的 **EEVDF** 取代 CFS）。
- **核心算法对比**：
  | 调度算法 | 核心策略 | 优缺点 |
  | :--- | :--- | :--- |
  | **FCFS (先来先服务)** | 队列顺序执行 | 公平无饥饿，但存在**护航效应**（长任务堵死后面一群短任务，平均等待时间长） |
  | **SJF / SRTF (短作业优先)** | 优先执行耗时最短的任务 | 理论上**平均等待时间最短**；但长作业可能永久**饥饿**，且耗时难以预知 |
  | **RR (时间片轮转)** | 固定时间片（如 10~100ms）循环剥夺切换 | 响应时间极佳（适合分时交互系统）；时间片太小则上下文切换开销爆表，太大退化为 FCFS |
  | **MLFQ (多级反馈队列)** | 多级队列优先级递减，时间片逐级倍增；新任务进高优队列，用完时间片降级 | **工业界集大成者**：既保证交互式短任务响应快，又避免长任务切换频繁，兼顾吞吐与响应 |
  | **Linux CFS (完全公平)** | 用**红黑树**按 `vruntime`（虚拟运行时间）排序，每次选 **`vruntime` 最小**的任务运行，优先级权重越高 `vruntime` 涨得越慢 | 无固定时间片，保证所有可运行任务按权重公平分摊 CPU；查找最左节点 $O(1)$，插入 $O(\log n)$ |
- **面试官连环追问**：
  1. **Java 线程优先级 `Thread.setPriority(1~10)` 为什么在生产中不建议依赖？**
     - JVM 只是将优先级映射为底层 OS 调度提示（Linux 下对应 `nice` 值），不同操作系统甚至容器调度策略可能完全忽略或弱化该提示，无法保证绝对的执行先后顺序。
- **实战避坑**：
  - 在多核服务器部署延迟敏感型服务（如交易撮合/Redis）时，可通过 `taskset` 绑核避免跨 CPU NUMA 节点和 L1/L2 缓存失效引起的延迟抖动。

### Q22：产生死锁的四个必要条件是什么？如何预防、避免（银行家算法）与检测解除？
- **直接结论**：
  - 死锁四条件（缺一不可）：**互斥、请求与保持、不可剥夺、循环等待**。工程中最高效的预防手段是**打破“循环等待”（按固定全局顺序加锁）**或**打破“请求与保持”（`tryLock` 超时放弃）**。
- **四大应对策略**：
  1. **预防死锁（破坏四条件之一）**：
     - 破坏互斥：尽量用无锁 CAS、原子类或 ThreadLocal 替代锁（如写时复制）。
     - 破坏请求与保持：一次性申请全部所需资源；或用 `ReentrantLock.tryLock(timeout)` 拿不到第二把锁就释放第一把。
     - 破坏不可剥夺：申请新资源失败时主动释放已占资源。
     - **破坏循环等待（最常用）**：给所有资源全局编号（如转账账户按 `min(fromId, toId)` 到 `max(fromId, toId)` 顺序加锁）。
  2. **避免死锁（银行家算法 Banker's Algorithm）**：
     - 每次分配资源前，先**预演**分配后系统是否还能找到一个**安全序列**（存在一条顺序能让所有进程依次拿足最大需求并顺利释放）；若找不到则处于**不安全状态**，拒绝本次分配。缺点是必须提前知道每个进程的最大资源需求，且 $O(m \cdot n^2)$ 算法开销大，现实 OS 极少采用。
  3. **检测与解除**：
     - 维护资源分配图检测环（如 MySQL InnoDB 死锁检测 `wait-for graph`）；发现死锁后剥夺资源或回滚代价最小的事务/杀死进程。
- **面试官连环追问**：
  1. **手写一段必定触发 Java 死锁的代码，并说明线上怎么三步定位？**
     - 两个线程分别先锁 `lockA` 再锁 `lockB`、先锁 `lockB` 再锁 `lockA`（中间 `sleep(100)` 确保彼此占住第一把锁）。
     - **线上定位**：`jps` 找到 PID → `jstack -l <pid>` → 在输出末尾查看 `Found one Java-level deadlock:` 直接精准定位到线程名、持有的锁对象地址及代码行号。
- **实战避坑**：
  - **死锁 vs 活锁 vs 饥饿**：死锁是线程全部永久 `BLOCKED/WAITING` 不动；**活锁**是线程都在运行不断退让（如两个线程拿不到第二把锁同时释放第一把再同时重试），CPU 可能飙高但毫无进展（引入随机退避时间即可打破活锁）。

### Q23：什么是虚拟内存？分段、分页与段页式管理原理？缺页中断与 TLB 是什么？
- **直接结论**：
  - **虚拟内存**让每个进程拥有独立、连续的逻辑地址空间（如 64 位系统 128TB 用户态空间），由 OS 和 CPU 的 **MMU（内存管理单元）** 通过**页表**按需映射到离散的物理页框或磁盘 Swap，实现**内存隔离**与**超越物理内存容量的程序运行**。
- **核心机制拆解**：
  1. **分页 vs 分段**：
     - **分页（Paging）**：将地址空间切分为固定大小的页（Linux 默认 **4KB**；大页 HugePage 2MB），解决外部碎片，对程序员透明；但无逻辑语义保护。
     - **分段（Segmentation）**：按逻辑模块（代码段、数据段、堆、栈）划分不等长段，方便权限控制与共享，但容易产生**外部内存碎片**。
     - **段页式**：先按逻辑分段，每段内再分页，兼顾保护与无外部碎片（现代 x86-64 Linux 弱化了分段，主要以平坦内存模型 + 多级分页为主）。
  2. **多级页表与 TLB 快表**：
     - 64 位地址若用单级页表内存直接爆炸；采用**4 级/5 级页表**（PGD → P4D → PUD → PMD → PTE）按需分配页表项，大幅节省内存。
     - **TLB（Translation Lookaside Buffer，转译后备缓冲器）**：MMU 内置的高速硬件缓存，专门缓存最近用过的 `虚拟页号 -> 物理页框号` 映射。命中 TLB 仅需 1 个时钟周期，未命中则需遍历内存中的多级页表（Page Table Walk）。
  3. **缺页中断（Page Fault）**：
     - 访问的虚拟页在页表中有效位为 0（未加载到物理内存）：CPU 触发缺页异常进入内核态 → 若物理内存充足直接分配物理页框（若在磁盘则从磁盘读入 Swap/mmap 文件）→ 更新页表 → 重新执行刚才被中断的指令。
- **面试官连环追问**：
  1. **为什么说 `malloc()` 分配了 1GB 内存并不代表物理内存立刻少了 1GB？**
     - `malloc()` 只是向内核申请扩展虚拟地址空间（建立 VMA 虚拟内存区域），内核采用**延迟分配（Demand Paging）**，只有当你真正向这片内存写入数据触发**缺页中断**时，才会实际分配物理页框并建立页表映射。
- **实战避坑**：
  - Java 高内存微服务（如 32GB+ 堆）若开启 Linux **透明大页（THP, Transparent Huge Pages）**，在内存碎片整理时可能导致内核同步卡顿（`khugepaged` 停顿数百毫秒），Redis、MySQL、Elasticsearch 官方均强烈建议生产关闭 THP（`echo never > /sys/kernel/mm/transparent_hugepage/enabled`）。

### Q24：常见页面置换算法有哪些？什么是 Belady 异常？LRU 和 LFU 有什么区别？
- **直接结论**：
  - 物理内存满且发生缺页时，操作系统需用页面置换算法淘汰旧页，常见算法有：**OPT（最佳置换，理论极限）、FIFO（先进先出）、LRU（最近最少使用）、LFU（最不经常使用）、Clock（二次机会算法）**。
- **核心算法对比**：
  | 算法 | 淘汰策略 | 优缺点与特性 |
  | :--- | :--- | :--- |
  | **OPT** | 淘汰**未来最长时间不再被访问**的页 | 缺页率最低，但无法预知未来，仅作理论基准 |
  | **FIFO** | 淘汰在内存中停留时间最长的页 | 实现简单（队列），但性能差，且存在 **Belady 异常**（分配的物理页框数增加，缺页次数反而上升！） |
  | **LRU** | 淘汰**最久未被访问**的页（按访问时间排序） | 利用时间局部性，性能接近 OPT，无 Belady 异常；**缺点**：偶发全表扫描（批量冷数据）会瞬间把热点缓存全部挤出（**缓存污染**） |
  | **LFU** | 淘汰**历史访问频率最低**的页（按次数排序） | 抗扫描污染能力强；**缺点**：早期高频旧热点长期占坑不退（需配合时间衰减 Aging 机制） |
  | **Clock (二次机会)** | 环形链表 + 访问位 `R`：淘汰时遇到 `R=1` 清 0 并跳过，遇到 `R=0` 淘汰 | **Linux 实际底层页面置换原型**（改进型 Dual-List Active/Inactive LRU 链表），兼顾 LRU 效果与低开销 |
- **面试官连环追问**：
  1. **手写 O(1) 时间复杂度的 LRU 缓存核心思路是什么？**
     - **哈希表（`HashMap<K, Node>`）+ 双向链表**：`HashMap` 保证 $O(1)$ 定位节点，双向链表保证 $O(1)$ 把刚访问的节点摘除并插入表头（最新）以及从表尾淘汰最旧节点。（Java 中可直接继承 `LinkedHashMap` 重写 `removeEldestEntry`，设置 `accessOrder = true`）。
  2. **MySQL InnoDB Buffer Pool 是如何解决原生 LRU 全表扫描污染问题的？**
     - 将 LRU 链表按 `5:3`（默认 `innodb_old_blocks_pct=37`）划分为 **Young 区（热数据）** 和 **Old 区（冷数据）**，新读入的页插在 **Old 区头部（中点插入）**，只有停留超过 `innodb_old_blocks_time`（默认 1000ms）后再次被访问，才晋升到 Young 区，完美过滤一次性全表扫描。
- **实战避坑**：
  - 缓存系统选型时，如果业务存在夜间批量跑批导出操作，纯 LRU 缓存（如默认配置前的 Redis）命中率会断崖下跌，此时应切换 Redis 的 **`allkeys-lfu`** 策略或为批处理单独隔离连接/绕过缓存。

### Q25：什么是用户态与内核态？切换方式及零拷贝（Zero-Copy）原理是什么？
- **直接结论**：
  - CPU 指令集划分权限环（x86 Ring 0 为**内核态**，可直接操作硬件与全部内存；Ring 3 为**用户态**，受限执行）。用户态切换内核态的 3 种方式：**系统调用（主动）、外设中断（被动）、CPU 异常（缺页/除零等）**。
- **传统文件传输 vs 零拷贝（Zero-Copy）对比**：
  - 场景：服务端将磁盘文件通过网卡发给客户端（`read()` + `write()`）。
  1. **传统 I/O（4 次上下文切换 + 4 次数据拷贝：2 次 DMA + 2 次 CPU）**：
     `磁盘 ─(DMA)─▶ 内核 PageCache ─(CPU)─▶ 用户态 Buffer ─(CPU)─▶ Socket 缓冲区 ─(DMA)─▶ 网卡`
  2. **`mmap` + `write`（4 次上下文切换 + 3 次拷贝）** *(RocketMQ CommitLog 采用)*：
     用户空间与内核 PageCache **共享内存映射**，省去 `PageCache -> 用户Buffer` 的 CPU 拷贝，适合小块数据高频读写。
  3. **`sendfile`（2 次上下文切换 + 2 次 DMA 拷贝，Linux 2.4+ SG-DMA）** *(Kafka、Nginx 静态文件采用)*：
     `磁盘 ─(DMA)─▶ 内核 PageCache ─(直接传递描述符与长度给 Socket Buffer，SG-DMA 直接从 PageCache 搬运)─▶ 网卡`
     全程 **0 次 CPU 拷贝**，且用户空间根本不经手数据！
- **面试官连环追问**：
  1. **Kafka 用 `sendfile` 这么快，为什么 RocketMQ 却选用了 `mmap`？**
     - `sendfile` 要求应用层**不能对数据做任何读取或修改**（直接转发整个文件块）；而 RocketMQ 的 Broker 在发送消息给消费者前，需要根据协议格式解析过滤或拼装轻量头信息，或者依赖 PageCache 随机偏移读写，因此选用 `mmap` 更灵活（代价是小数据写入需注意 `MappedByteBuffer` 内存释放问题）。
  2. **大文件传输（如几个 GB 视频）适合用 `sendfile`（走 PageCache）吗？**
     - 不适合！大文件会瞬间把内核 PageCache 全部洗掉（热点小文件缓存全失效），此时应使用 **异步 IO + `Direct I/O`（绕过内核缓冲区直接读写磁盘）**（Nginx 大文件可通过 `directio` 指令自动切换）。
- **实战避坑**：
  - Java NIO 中 `FileChannel.transferTo()` 底层在 Linux 上正是调用 **`sendfile()`** 系统调用；注意单次调用某些旧版本内核有 2GB 限制，大文件需循环累加传输偏移量。

### Q26：Linux 的五种 I/O 模型是什么？同步 I/O 与异步 I/O 的本质区别？
- **直接结论**：
  - 五种 I/O 模型：**阻塞 I/O（BIO）、非阻塞 I/O（NIO）、I/O 多路复用、信号驱动 I/O（SIGIO）、异步 I/O（AIO）**。
  - 按 POSIX 标准，**前四种全部属于同步 I/O**（因为第二阶段数据从内核拷贝到用户空间时，应用线程仍需同步阻塞等待）；只有第五种 **AIO 是真正的异步 I/O**（两个阶段均由内核完成后回调通知）。
- **一次完整网络读 I/O 的两个阶段**：
  - **阶段 1**：等待数据从网卡到达内核缓冲区（Wait for data）。
  - **阶段 2**：将数据从内核缓冲区拷贝到用户进程空间（Copy data from kernel to user）。
- **五种模型对照图**：
  | I/O 模型 | 阶段 1（等数据就绪） | 阶段 2（内核拷贝到用户态） | 适用场景 / 特点 |
  | :--- | :--- | :--- | :--- |
  | **阻塞 I/O (BIO)** | **阻塞** | **阻塞** | 编程最简单，一连接一线程，高并发线程爆炸 |
  | **非阻塞 I/O (NIO)** | **非阻塞轮询**（返回 `EWOULDBLOCK`） | **阻塞** | 不断死循环空耗 CPU，极少单独直接用 |
  | **I/O 多路复用** | **阻塞在 `select/epoll_wait` 上**（同时监听成千上万 FD） | **阻塞**（`recv` 读取就绪 FD 数据） | **高并发网络编程核心基石**（Redis、Nginx、Netty） |
  | **信号驱动 I/O** | 非阻塞（内核发 `SIGIO` 通知） | **阻塞** | 较少用于 TCP 高并发（TCP 信号太频繁难以区分事件） |
  | **异步 I/O (AIO)** | **非阻塞** | **非阻塞**（内核拷贝完毕后再回调） | Linux 原生 `aio` 主要支持磁盘文件且有缺陷；Linux 5.1+ **`io_uring`** 才是划时代真异步 |
- **面试官连环追问**：
  1. **为什么 Netty 在 Linux 上放弃了看似更高级的 Java AIO，依然坚持使用基于 `epoll` 的 NIO？**
     - Linux 早期内核原生 AIO（`libaio`）对网络 Socket 支持不成熟（底层实际仍借助线程池模拟），性能反而不如高度优化的 `epoll`；此外多路复用模型调优成熟且控制粒度细（Linux 新一代 `io_uring` 已开始在 Netty Incubator 中接入）。
- **实战避坑**：
  - 区分“同步/异步”看的是**第二阶段数据拷贝谁来做（内核通知还是自己去读）**；区分“阻塞/非阻塞”看的是**调用在数据没准备好时是挂起等待还是立即返回**。

### Q27：`select`、`poll`、`epoll` 底层原理与核心区别？LT 与 ET 模式及惊群效应？
- **直接结论**：
  - `select` 和 `poll` 每次调用都需要把全量 FD 集合从用户态拷贝到内核态并 $O(n)$ 轮询所有 FD；`epoll` 通过内核中的 **红黑树 + 就绪双向链表 + 回调机制** 实现 **$O(1)$** 获取活跃连接，性能不随总连接数增长而下降。
- **三者底层对比**：
  | 对比维度 | `select` | `poll` | `epoll` |
  | :--- | :--- | :--- | :--- |
  | **数据结构** | 固定大小位图 `fd_set` | 动态数组 `pollfd[]` | **红黑树**（存监听 FD）+ **就绪链表 `rdlist`** |
  | **最大连接数** | 受限于 `FD_SETSIZE`（默认 **1024**） | 无上限（受限于内存与 ulimit） | 无上限（受限于系统最大打开文件数） |
  | **内存拷贝** | 每次调用都全量用户态↔内核态拷贝 | 每次调用都全量用户态↔内核态拷贝 | `epoll_ctl` 注册一次即可，后续无需重复拷贝全集 |
  | **寻找就绪 FD** | 内核 + 用户态均需 $O(n)$ 遍历全部 FD | 内核 + 用户态均需 $O(n)$ 遍历全部 FD | **$O(1)$**（网卡中断触发回调函数直接把就绪 FD 塞入 `rdlist`） |
- **`epoll` 两种触发模式（LT vs ET）**：
  - **LT（Level Trigger，水平触发，默认）**：只要内核缓冲区还有数据可读，每次调用 `epoll_wait` 都会反复通知你，编程安全不易丢事件（Redis、Java NIO Selector 默认）。
  - **ET（Edge Trigger，边缘触发）**：仅在缓冲区状态**从无到有（发生变化）时通知一次**！哪怕这次你没读完，下次也不会再通知。因此 **ET 必须配合非阻塞 Socket，并在一个循环中把缓冲区彻底读空直到返回 `EAGAIN`**。好处是减少大量重复 `epoll_wait` 系统调用开销（Nginx、Netty Epoll native transport 默认开启）。
- **面试官连环追问**：
  1. **什么是 `epoll` 惊群效应？Nginx 是怎么解决的？**
     - 当多个 Worker 进程同时监听同一个端口的 `epoll` 实例，一个新连接到来时所有睡眠的 Worker 都会被唤醒抢着去 `accept()`，但只有一个能抢到，其余白白浪费上下文切换。
     - **解决**：早期 Nginx 用全局 **`accept_mutex`** 互斥锁保证同一时刻只有一个 Worker 把监听 FD 挂入自己的 `epoll`；Linux 3.9+ 引入 **`SO_REUSEPORT`**，允许多个进程各自绑定同一端口，内核直接按四元组 Hash 将新连接均匀分发给单个 Worker，彻底消除惊群！
- **实战避坑**：
  - 高并发服务部署在 Linux 上经常遇到 `Too many open files` 报错，务必检查并调大 `/etc/security/limits.conf` 中的 `nofile` 限制（如 `65535` 或 `1048576`），同时注意 systemd 启动的服务不读 `limits.conf`，要在 `.service` 文件中单独配 `LimitNOFILE=1048576`。

### Q28：Linux 高频性能监控命令实战：`top`、`vmstat`、`iostat`、`free`、`uptime` 如何解读？
- **直接结论**：
  - 线上排查性能瓶颈的黄金五分钟原则：**先 `uptime` / `top` 看整体负载与 CPU/内存归属 → 再 `vmstat` 看上下文切换与运行队列 → 再 `iostat` 看磁盘 IO 等待 → 再 `free` 看真实可用内存**。
- **核心命令与关键指标拆解**：
  1. **`uptime` 与 Load Average**：
     - 显示过去 1 分钟、5 分钟、15 分钟平均负载（等待 CPU 运行 + 处于**不可中断睡眠 `D` 状态**等 IO 的平均进程数）。
     - **判定标准**：当 1 分钟负载持续大于 `CPU 核数 × 0.7~1.0` 且呈上升趋势时系统过载。若 Load 高但 `%us + %sy` 低，往往是大量进程卡在磁盘/网络 IO（`wa` 高）！
  2. **`top`（按 `1` 展开所有核，按 `P` 按 CPU 排，按 `M` 按内存排，`top -Hp <pid>` 查进程内线程）**：
     - `%us`（用户态 CPU）：高说明业务代码死循环、正则回溯、频繁序列化或密集计算。
     - `%sy`（内核态 CPU）：高说明频繁系统调用、锁竞争或线程上下文切换剧烈。
     - **`%wa`**（iowait）：CPU 空等磁盘 IO 的时间占比，高说明磁盘瓶颈或大刷盘/Swap。
     - **`%si`**（软中断）：高常见于高并发网络包收发（网卡软中断瓶颈）。
  3. **`vmstat 1 5`（每秒采样一次，共 5 次）**：
     - `r`（运行队列长度，长期大于 CPU 核数说明 CPU 算力不足）、`b`（阻塞在 IO 的进程数）。
     - `si` / `so`（Swap In/Out）：只要持续非 0，说明物理内存严重不足开始疯狂换页，性能必崩！
     - `cs`（Context Switch 上下文切换次数）与 `in`（中断次数）：突增说明线程过多或锁争抢严重。
  4. **`iostat -xz 1`**：
     - `%util` 接近 100% 说明磁盘饱和；`await`（单次 IO 平均响应毫秒数，SSD 正常 < 1~5ms）远大于 `svctm` 说明 IO 队列排队严重。
  5. **`free -h`**：
     - 重点看 **`available`**（真正可用的内存，包含可随时回收的 PageCache `buff/cache`），而不是直接看 `free`（Linux 会主动把空闲内存用来做磁盘缓存，导致 `free` 很小但系统完全健康）。
- **面试官连环追问**：
  1. **Java 应用 CPU 突然飙到 100% 怎么在 1 分钟内精准定位到具体代码行？**
     - 四步连招：`top` 找最耗 CPU 的 Java `pid` → `top -Hp <pid>` 找最耗 CPU 的线程 `tid` → `printf "%x\n" <tid>` 转 16 进制 → `jstack <pid> | grep -A 30 <16进制tid>` 直接看业务代码堆栈行号（或直接上 Arthas 的 `thread -n 3` 一条命令秒杀）。
- **实战避坑**：
  - 容器环境（Docker/K8s）里宿主机命令与容器 cgroup 视图可能不一致，用 `top` 时留意看容器 CPU Limit 限制（CFS Quota throttling）而非仅仅看宿主机 CPU 总核数。

### Q29：Linux 网络、端口、抓包与进程文件句柄排查命令怎么配合使用？
- **直接结论**：
  - 现代 Linux 排查网络首选 **`ss`**（直接读取内核 `netlink` 套接字信息，比遍历 `/proc` 的 `netstat` 快百倍）；抓包神器用 **`tcpdump`**；查文件句柄与进程占用用 **`lsof`**；服务管理用 **`systemctl`** 和 **`journalctl`**。
- **高频组合命令速查**：
  1. **连接与端口排查（`ss` / `netstat`）**：
     - `ss -tulpn`：查看所有正在监听的 TCP/UDP 端口及对应进程 PID/程序名。
     - `ss -antp | grep :3306`：查看所有到 3306 端口的连接状态及两端进程。
     - `ss -s`：快速汇总系统当前各 TCP 连接状态的总体数量。
  2. **精准抓包分析（`tcpdump`）**：
     - `tcpdump -i eth0 host 10.0.1.5 and port 8080 -nn -vv -w capture.pcap`：抓取指定网卡、IP 和端口的数据包存成 pcap，拉到本地用 Wireshark 图形化分析三次握手、RST、重传或 TLS 报错。
     - `-nn` 不把 IP/端口反解为域名和服务名（极大提升抓包速度防止丢包）。
  3. **句柄与服务状态排查（`lsof` / `systemctl`）**：
     - `lsof -i :8080`：查谁占用了 8080 端口。
     - `lsof +L1` 或 `lsof | grep deleted`：排查**“磁盘空间 `df -h` 显示已满 100%，但 `du -sh /*` 统计目录大小加起来才用了一半”**的经典诡异故障——原因就是大日志文件被 `rm` 删除了，但 Java/Nginx 进程仍持有其 FD 句柄未关闭，导致内核未真正释放磁盘块！重启进程或 `> /proc/<pid>/fd/<fd号>` 清空即可瞬间释放空间。
     - `systemctl status nginx` / `journalctl -u nginx -f --since "10 minutes ago"`：查看守护进程状态及 systemd 崩溃启动日志。
- **面试官连环追问**：
  1. **为什么不要用 `rm -rf` 直接删正在写入的线上大日志？应该怎么安全清理？**
     - 因为进程持有文件句柄直接 `rm` 空间并不会释放，反而让你再也找不到文件位置。正确做法是使用 **`truncate -s 0 app.log`** 或 **`cat /dev/null > app.log`**（保留 inode 与句柄，立刻把文件大小清零释放块），并配置 `logrotate` 或 Logback 滚动策略。
- **实战避坑**：
  - `tcpdump` 在高流量生产网卡上抓包时，**务必加上精确过滤表达式（如 `port` 和 `host`）及 `-c 10000` 抓包上限**，千万不要裸跑无过滤的 `tcpdump -i eth0`，否则极易瞬间打爆磁盘或造成业务严重丢包抖动。

### Q30：Linux 文本与日志分析三剑客（`grep`、`awk`、`sed`）及 `find` 高频实战命令？
- **直接结论**：
  - **`grep`** 负责行级快速过滤匹配；**`sed`** 负责流式行编辑替换；**`awk`** 负责按列切分、聚合统计与格式化输出；**`find`** 负责按文件属性搜索并配合 `xargs` 批量处理。
- **一线开发高频生产实战组合**：
  1. **日志错误定位（`grep`）**：
     - `grep -rnE "ERROR|Exception" /var/log/app/`：递归带行号正则匹配。
     - `grep -C 15 "OutOfMemoryError" app.log`：查看异常前后各 15 行上下文（`-A` 后几行，`-B` 前几行）。
     - `zgrep "orderId=12345" app.2026-11-18.log.gz`：无需解压直接搜索 `.gz` 归档压缩日志！
  2. **接口耗时 Top N / 状态码统计（`awk`）**：
     - 统计 Nginx `access.log` 访问次数 Top 10 IP：
       `awk '{print $1}' access.log | sort | uniq -c | sort -nr | head -10`
     - 统计某接口（第 7 列 URL，最后一列耗时 `$NF`）平均耗时与最大耗时：
       `awk '$7 ~ /\/api\/order/ {sum+=$NF; count++; if($NF>max) max=$NF} END {printf "count=%d avg=%.3f max=%.3f\n", count, sum/count, max}' access.log`
  3. **精准截取时间段日志或替换配置（`sed`）**：
     - 截取今天 `14:00` 到 `14:05` 之间的所有日志（无需手动翻页）：
       `sed -n '/2026-11-18 14:00/,/2026-11-18 14:05/p' app.log > slice.log`
     - 批量原地替换配置文件属性（`-i.bak` 自动备份）：
       `sed -i.bak 's/old_host/new_host/g' config.yml`
  4. **安全清理历史大文件（`find`）**：
     - 查找超过 7 天且大于 100MB 的 `.log` 文件并安全清理：
       `find /data/logs -type f -name "*.log" -mtime +7 -size +100M -print0 | xargs -0 rm -f`
       *(注：`-print0` + `xargs -0` 用 `\0` 分隔，防止文件名含空格误删其他文件！)*
- **面试官连环追问**：
  1. **`sort | uniq -c` 为什么必须先 `sort` 再 `uniq`？**
     - 因为 Linux `uniq` 命令**只去重相邻的重复行**！如果不先 `sort` 让相同行挨在一起，隔开出现的相同 IP 是不会被合并计数的。
- **实战避坑**：
  - 在几 GB 级别的超大日志文件上运行 `grep` 时，如果只匹配固定字符串不需正则，加上 **`-F`**（或用 `LC_ALL=C grep` 关闭本地化 UTF-8 复杂字符集解析），搜索速度可暴涨 5~10 倍！

## 3. 面向对象原则与设计模式源码级解析（Q31 ~ Q43）

### Q31：面向对象设计的六大原则（SOLID + 迪米特法则 LoD）是什么？
- **直接结论**：
  - 面向对象架构设计的基石是 **SOLID 五大原则 + 迪米特法则（LoD）+ 合成复用原则**，总目标只有一句话：**高内聚、低耦合，让代码易于扩展和维护**。
- **核心原则逐条精解**：
  | 原则名称 | 核心定义 | 实战落地与反面教材 |
  | :--- | :--- | :--- |
  | **单一职责原则 (SRP)** | 一个类/方法只负责一项单一业务职责（只有一个引起它变化的原因） | 反例：`UserService` 里既写登录鉴权、又写发邮件、还写导 Excel；正例：拆分为鉴权、通知、导出组件 |
  | **开闭原则 (OCP，总纲)** | **对扩展开放，对修改关闭** | 新增支付渠道（如 ApplePay）时只需新增一个策略实现类，而不是去修改原有 `switch-case` 核心代码 |
  | **里氏替换原则 (LSP)** | 所有引用基类的地方必须能透明地使用其子类对象，不能破坏父类原有契约 | 经典反例：正方形继承长方形并重写 `setWidth()` 同时改高度，导致断言 `w * h` 失败 |
  | **接口隔离原则 (ISP)** | 客户端不应被迫依赖它不需要的接口（拆分为小而专的接口） | 把臃肿的 `AnimalService` 拆为 `Flyable`、`Swimmable`，而不是让狗被迫实现 `fly()` 空抛异常 |
  | **依赖倒置原则 (DIP)** | 高层模块不依赖低层模块，**两者都应依赖抽象**；抽象不应依赖细节 | 业务层注入 `PayGateway` 接口而非 `AlipayClientImpl` 具体类（Spring IoC / DI 的理论核心） |
  | **迪米特法则 (LoD / 最少知道原则)** | 一个对象应当对其他对象有尽可能少的了解，只和直接朋友通信 | 避免链式深挖调用 `order.getUser().getAddress().getCity().getZipCode()`，改为直接提供封装方法 `order.getShippingZipCode()` |
  | **合成复用原则 (CRP)** | **优先使用对象组合/聚合**，而不是类继承来实现代码复用 | 继承是强耦合白盒复用（父类改动牵一发全身），组合是弱耦合黑盒复用（如 Java IO 装饰器流） |
- **面试官连环追问**：
  1. **遵循单一职责和接口隔离原则，把类拆得越细越好吗？**
     - 过度拆解会导致**类爆炸**，调用链过长难以阅读理解。设计原则是指导思想而非教条：应在“当前业务真实变化点”处做抽象隔离，避免过早过度设计。
- **实战避坑**：
  - 看到几十行的 `if-else` 渠道判断或硬编码 `new ConcreteDao()` 时，立刻思考是否违反了 **OCP** 和 **DIP**。

### Q32：单例模式（Singleton）有哪 5 种以上经典实现？如何防止反射和反序列化破坏？
- **直接结论**：
  - 生产级线程安全单例有 5 种典型写法：**饿汉式、双重检查锁（DCL + `volatile`）、静态内部类（Holder）、枚举单例（《Effective Java》最推荐）、容器/Spring 注册式单例**。其中**只有枚举单例天然免疫反射和反序列化攻击**。
- **5 种写法核心实现代码**：
  ```java
  // 1. 饿汉式：类加载即初始化（JVM 保证线程安全，缺点：无法懒加载）
  public class EagerSingleton {
      private static final EagerSingleton INSTANCE = new EagerSingleton();
      private EagerSingleton() {}
      public static EagerSingleton getInstance() { return INSTANCE; }
  }

  // 2. 双重检查锁 DCL（懒加载 + 高并发低锁开销）
  public class DclSingleton {
      // 必须加 volatile：禁止 new DclSingleton() 的指令重排（防止其他线程拿到半初始化对象）
      private static volatile DclSingleton instance;
      private DclSingleton() {}
      public static DclSingleton getInstance() {
          if (instance == null) {                      // 第一次检查：避免每次都加锁
              synchronized (DclSingleton.class) {
                  if (instance == null) {              // 第二次检查：防止多线程同时通过第一次检查
                      instance = new DclSingleton();
                  }
              }
          }
          return instance;
      }
  }

  // 3. 静态内部类（懒加载 + 无锁线程安全，利用 JVM 类初始化锁 <clinit>）
  public class HolderSingleton {
      private HolderSingleton() {}
      private static class Holder {
          private static final HolderSingleton INSTANCE = new HolderSingleton();
      }
      public static HolderSingleton getInstance() { return Holder.INSTANCE; }
  }

  // 4. 枚举单例（最安全：防反射、防反序列化、线程安全）
  public enum EnumSingleton {
      INSTANCE;
      public void doWork() { System.out.println("working"); }
  }

  // 5. 注册式单例（类似 Spring DefaultSingletonBeanRegistry 核心思想）
  public class ContainerSingleton {
      private static final Map<String, Object> IOC = new ConcurrentHashMap<>();
      public static Object getBean(String className) {
          return IOC.computeIfAbsent(className, k -> {
              try { return Class.forName(k).getDeclaredConstructor().newInstance(); }
              catch (Exception e) { throw new RuntimeException(e); }
          });
      }
  }
  ```
- **防破坏原理与框架源码应用**：
  - **防反射破坏**：`Constructor.newInstance()` 源码中明确判断如果类是 `Modifier.ENUM` 则直接抛出 `Cannot reflectively create enum objects`。普通类需在私有构造器里校验 `if (instance != null) throw new RuntimeException()`。
  - **防反序列化破坏**：普通类实现 `Serializable` 后反序列化会走反射创建新对象，需定义 `private Object readResolve() { return INSTANCE; }` 替换返回值；而枚举类反序列化直接走 `Enum.valueOf()` 查表返回唯一实例。
  - **框架源码**：`java.lang.Runtime`（饿汉式）、`System.console()`（DCL）、Spring `DefaultSingletonBeanRegistry`（三级缓存 ConcurrentHashMap 注册式单例）。
- **面试官连环追问**：
  1. **DCL 中的 `volatile` 如果不加，在什么极端瞬间会出 Bug？**
     - `instance = new DclSingleton()` 分三步：1) 分配内存；2) 初始化对象；3) 将 `instance` 引用指向内存地址。JVM/CPU 可能把步骤 2 和 3 **指令重排**！若线程 A 刚执行完 1 和 3 还未执行 2，线程 B 进来看到 `instance != null` 直接拿去使用，就会读到字段全为默认零值的**半初始化对象**。
- **实战避坑**：
  - Spring 默认的 `singleton` 作用域是**每个 `ApplicationContext` 容器内单实例**，并非 JVM 全局唯一（如果同一个类在容器里配了两个不同 `beanName`，依然会有两个对象）。

### Q33：简单工厂、工厂方法、抽象工厂的区别是什么？在 JDK 和 Spring 中如何应用？
- **直接结论**：
  - **简单工厂**（静态方法 + `if/switch`）违反开闭原则；**工厂方法**为每种产品定义一个具体工厂实现类，符合开闭原则；**抽象工厂**用于创建**一整个产品族（相互关联的多个组件）**。
- **三者演化对比与框架应用**：
  | 模式 | 核心结构 | 适用场景 | JDK / Spring / MyBatis 源码映射 |
  | :--- | :--- | :--- | :--- |
  | **简单工厂** | 一个工厂类包揽所有同类对象创建 | 产品种类少且稳定 | `Calendar.getInstance()`、`Executors.newFixedThreadPool()`、MyBatis `SqlSessionFactoryBuilder` |
  | **工厂方法** | 抽象工厂接口 + 多个具体工厂子类（一对一） | 随时需扩展新产品类型 | Spring **`FactoryBean<T>`**（`getObject()`）、SLF4J `ILoggerFactory` |
  | **抽象工厂** | 抽象工厂接口定义多个关联产品创建方法 | 跨平台 UI 套件、全套数据库驱动套件 | JDBC `Connection`（生产 `Statement`、`PreparedStatement`）、Spring **`BeanFactory`** |
- **面试官连环追问**：
  1. **Spring 中 `BeanFactory` 和 `FactoryBean` 的区别是什么？（高频连环必杀题）**
     - **`BeanFactory`** 是整个 Spring IoC 容器的顶层接口（大工厂），负责管理成千上万个 Bean 的生命周期与依赖注入。
     - **`FactoryBean`** 是一个**特殊的 Bean 接口**（小工厂，实现了工厂方法模式），用来定制复杂对象（如 MyBatis `SqlSessionFactoryBean`、ProxyFactoryBean）的创建过程：当向容器 `getBean("myBean")` 时，如果它是 `FactoryBean`，容器默认返回的是其 `getObject()` 产出的对象；想拿到 `FactoryBean` 本身则需加前缀 `getBean("&myBean")`。
- **实战避坑**：
  - 引入第三方 SDK 初始化极度复杂（如校验签名、建立连接池、读取多层配置）时，在 Spring 中不要写一堆 `@Bean` 杂糅代码，封装一个 `FactoryBean` 最优雅。

### Q34：建造者模式（Builder）与原型模式（Prototype）适用场景？深拷贝与浅拷贝如何实现？
- **直接结论**：
  - **建造者模式**解决**多参数复杂对象的分步构建与参数校验**，避免构造器参数列表爆炸（伸缩构造函数反模式）；**原型模式**通过拷贝现有对象来高效创建新对象（跳过昂贵构造器/IO），在 Java 中需格外区分**浅拷贝与深拷贝**。
- **核心原理与源码映射**：
  1. **建造者模式（Builder）**：
     - 常见链式调用变体：Lombok `@Builder`、OkHttp `Request.Builder`、`StringBuilder`、Spring `BeanDefinitionBuilder`、MyBatis `SqlSessionFactoryBuilder` / `MappedStatement.Builder`。
     - **与工厂模式区别**：工厂模式关心“**创建出什么产品**”（一步到位直接返回结果）；建造者模式关心“**产品各部件按什么顺序和参数组装**”。
  2. **原型模式（Prototype）**：
     - **浅拷贝**：实现 `Cloneable` 并重写 `super.clone()`，基本类型拷贝值，**引用类型只拷贝内存地址（原对象与克隆体共享内部引用对象！）**。
     - **深拷贝实现方式**：
       1. 各层引用类均递归实现 `Cloneable` 重写 `clone()`（代码繁琐）。
       2. 序列化反序列化（JDK 原生 `ObjectOutputStream` 要求实现 `Serializable` 性能较差，生产常用 Jackson/Kryo 或 Apache Commons `SerializationUtils`）。
       3. Spring `scope="prototype"` 每次 `getBean` 都重新创建新实例（如多例 Controller/任务对象）。
- **面试官连环追问**：
  1. **为什么 `Object.clone()` 方法被设计为 `protected`，而且不实现 `Cloneable` 接口调用它会抛 `CloneNotSupportedException`？**
     - `Cloneable` 是一个空标记接口（Marker Interface），JVM 底层本地方法 `Object.clone()` 会检查目标对象是否实现了该标记接口，没实现则拒绝按内存字节块拷贝；设计成 `protected` 是防止外部随意克隆没有做好深拷贝处理的对象导致共享状态错乱。
- **实战避坑**：
  - `BeanUtils.copyProperties(src, dest)`（Spring 或 Apache）执行的是**浅拷贝**！如果 DTO 里包含嵌套 `List<Item>` 或子对象，拷贝后修改子对象属性会反向污染源对象；此外 Spring `BeanUtils` 性能远优于 Apache `BeanUtils`（后者用了大量反射校验和日志），高频大批量转换推荐编译期生成代码的 **MapStruct**。

### Q35：代理模式（静态代理、JDK 动态代理、CGLIB）原理与区别？在 Spring/MyBatis 中怎么用的？
- **直接结论**：
  - 代理模式为目标对象提供一个替身以控制访问并织入增强逻辑（日志、事务、鉴权、RPC 远程调用）。**JDK 动态代理基于接口生成 `$ProxyN` 代理类；CGLIB 基于 ASM 修改字节码生成目标类的子类**。
- **三种代理方式全面对比**：
  | 维度 | 静态代理 | JDK 动态代理 | CGLIB 动态代理 |
  | :--- | :--- | :--- | :--- |
  | **实现机制** | 手动编写代理类实现相同接口 | `Proxy.newProxyInstance()` + `InvocationHandler`，运行期动态生成实现接口的字节码 | 基于 ASM 字节码框架，运行期生成**继承目标类**的子类 + `MethodInterceptor` |
  | **目标类限制** | 需手工维护，代码冗余 | **必须实现至少一个接口** | **不能代理 `final` 类及 `final`/`private` 方法** |
  | **调用效率** | 直接方法调用，最快 | 早期反射调用较慢，JDK 8+ 经 JIT 优化后与 CGLIB 相当 | 通过 `FastClass` 索引直接调用方法，避开反射 |
- **JDK 与 CGLIB 核心源码映射**：
  - **Spring AOP**：`DefaultAopProxyFactory` 判断目标类是否实现接口（且 `proxyTargetClass=false`）选择 `JdkDynamicAopProxy`，否则用 `ObjenesisCglibAopProxy`。注意 **Spring Boot 2.x 起默认 `spring.aop.proxy-target-class=true` 统一优先使用 CGLIB**（防止按具体类注入 `@Autowired UserServiceImpl` 时因只代理了接口而启动报错）。
  - **MyBatis**：`MapperProxyFactory` 为只有接口没有实现类的 `UserMapper` 生成 **JDK 动态代理 `MapperProxy`**，拦截方法名去匹配 XML 中的 `MappedStatement` 并执行 SQL！
  - **Dubbo / OpenFeign**：为消费端 `@DubboReference` / `@FeignClient` 接口生成代理对象，将本地方法调用透明封装成网络 RPC 请求。
- **面试官连环追问**：
  1. **为什么同一个 Service 类内部方法 `this.methodB()` 调用带 `@Transactional` 或 `@Async` 的方法，注解会失效？**
     - 因为 `this` 指向的是**目标原始对象本身**，而不是 Spring 容器生成的**代理对象**，绕过了代理拦截链！**解决**：拆到另一个 Bean 中、通过 `AopContext.currentProxy()` 获取代理对象调用，或自己注入自己（注意构造器循环依赖）。
- **实战避坑**：
  - 别把加了 `@Transactional` / `@Cacheable` 的方法声明为 `private` 或 `final`，CGLIB 无法重写 `final`/`private` 方法，注解会静默失效不报错！

### Q36：装饰器模式（Decorator）与适配器模式（Adapter）的本质区别与源码应用？
- **直接结论**：
  - **装饰器模式**是**“同接口增强”**：输入输出接口完全不变，通过层层嵌套包装动态叠加新功能（比继承更灵活）；**适配器模式**是**“异接口转换”**：将一个不兼容的已有接口转换成调用方期望的另一个目标接口。
- **核心对比与框架源码映射**：
  | 对比维度 | 装饰器模式 (Decorator) | 适配器模式 (Adapter) |
  | :--- | :--- | :--- |
  | **核心意图** | **增强功能**，保持原接口规范不变 | **接口兼容**，抹平两个不匹配接口之间的差异 |
  | **结构关系** | 装饰类与被装饰类实现**同一个接口** | 适配器实现目标接口，内部组合/继承被适配者 |
  | **JDK 源码** | `BufferedInputStream(new FileInputStream(...))`<br>`Collections.synchronizedList(list)` | `Arrays.asList(arr)`（数组转 List）<br>`InputStreamReader(inputStream)`（字节流适配为字符流） |
  | **Spring / MyBatis 源码** | Spring Session `SessionRepositoryRequestWrapper`<br>MyBatis `CachingExecutor`（包装 `SimpleExecutor` 增加二级缓存功能） | **Spring MVC `HandlerAdapter`**（把 `@Controller`、`HttpRequestHandler`、`Servlet` 统一适配成标准处理流程）<br>**MyBatis `Log` 适配层**（统一适配 Log4j2、SLF4J、JUL）<br>Spring AOP `AdvisorAdapter` |
- **面试官连环追问**：
  1. **装饰器模式和静态代理模式代码长得几乎一模一样，怎么区分它们？**
     - 看**目的与关系**：装饰器强调**动态组合多层功能**，客户端知道自己包了几层（`new BufferedReader(new InputStreamReader(fileStream))`）；代理模式强调**控制访问与职责隔离**，客户端往往感知不到真实对象的存在（代理内部隐藏或延迟创建真实对象）。
- **实战避坑**：
  - 多层装饰器嵌套不要超过 3~4 层，否则排查问题单步 Debug 时栈深太深、初始化和包装对象过多。

### Q37：桥接、外观、组合、享元模式各自解决什么痛点？对应哪些经典源码？
- **直接结论**：
  - 这四个结构型模式分别解决：**多维度独立变化（桥接）、简化复杂子系统调用（外观）、树形整体与部分统一操作（组合）、海量细粒度对象内存复用（享元）**。
- **四大模式源码级速查表**：
  | 模式 | 核心痛点与解决方案 | 经典源码案例 |
  | :--- | :--- | :--- |
  | **桥接模式 (Bridge)** | 当一个类存在**两个以上独立变化维度**（如“消息类型：邮件/短信” × “紧急程度：普通/加急”），用组合代替多层继承，避免 $M \times N$ 类爆炸 | **JDBC `DriverManager` + `Driver`**（JDBC 抽象 API 与各厂商 MySQL/Oracle 驱动实现解耦桥接）、SLF4J 门面与日志实现桥接 |
  | **外观模式 (Facade)** | 为复杂的多个内部子系统提供一个**统一的高层简化入口**，遵循迪米特法则 | **Tomcat `RequestFacade` / `ResponseFacade`**（屏蔽内部敏感对象，仅暴露 Servlet 标准接口）、**SLF4J**、Spring `JdbcUtils` |
  | **组合模式 (Composite)** | 将对象组织成**树形结构**，使客户端对单个叶子节点和组合容器节点一视同仁 | **MyBatis 动态 SQL `SqlNode`**（`MixedSqlNode` 包含多个 `IfSqlNode`/`WhereSqlNode`）、Spring MVC `CompositeView`、Java AWT/Swing 组件树 |
  | **享元模式 (Flyweight)** | 系统中存在大量重复细粒度对象时，抽离**内部状态（不可变共享）**与**外部状态（传入参数）**进行池化复用，极大节省内存 | **JDK `Integer.valueOf()` (`IntegerCache` -128~127)**、**`String` 常量池**、**Netty `Recycler` / `PooledByteBufAllocator`**、数据库连接池/线程池 |
- **面试官连环追问**：
  1. **享元模式和单例模式有什么区别？**
     - 单例是整个系统**只有 1 个唯一实例**；享元是系统中有**有限多个可共享的可复用实例池**（例如 256 个缓存的 `Integer` 对象，或者棋盘上的黑棋/白棋两个共享棋子对象，坐标作为外部状态传入）。
- **实战避坑**：
  - 使用 Netty 池化 `ByteBuf`（享元模式）时，如果申请后忘记调用 `ReferenceCountUtil.release(buf)` 归还引用计数，会引发致命的**堆外直接内存泄漏**。

### Q38：策略模式（Strategy）如何结合 Spring `Map` 注入彻底消灭业务 `if-else`？
- **直接结论**：
  - 策略模式定义一系列可互相替换的算法族并分别封装；在 Spring Boot 生产开发中，利用 **Spring 自动将同一接口的所有实现 Bean 注入到 `Map<String, Strategy>`**（结合枚举路由），新增业务渠道时只需新增一个实现类，实现真正的**零修改开闭原则（OCP）**。
- **生产级完整 Java 代码示例**：
  ```java
  // 1. 定义策略接口
  public interface PayStrategy {
      String channel(); // 返回渠道标识，如 "ALIPAY" / "WECHAT"
      PayResult pay(PayRequest req);
  }

  // 2. 具体策略实现（自动注册为 Spring Bean）
  @Component
  public class AlipayStrategy implements PayStrategy {
      @Override public String channel() { return "ALIPAY"; }
      @Override public PayResult pay(PayRequest req) { /* 支付宝逻辑 */ return PayResult.ok(); }
  }

  @Component
  public class WechatPayStrategy implements PayStrategy {
      @Override public String channel() { return "WECHAT"; }
      @Override public PayResult pay(PayRequest req) { /* 微信支付逻辑 */ return PayResult.ok(); }
  }

  // 3. 策略上下文路由工厂（构造器注入所有实现）
  @Service
  public class PayContext {
      private final Map<String, PayStrategy> strategyMap;

      public PayContext(List<PayStrategy> strategies) {
          this.strategyMap = strategies.stream()
                  .collect(Collectors.toMap(PayStrategy::channel, Function.identity()));
      }

      public PayResult executePay(String channel, PayRequest req) {
          PayStrategy strategy = Optional.ofNullable(strategyMap.get(channel))
                  .orElseThrow(() -> new IllegalArgumentException("不支持的支付渠道: " + channel));
          return strategy.pay(req);
      }
  }
  ```
- **JDK/Spring 经典源码**：
  - JDK 线程池 **`RejectedExecutionHandler`**（`AbortPolicy`、`CallerRunsPolicy` 等 4 种拒绝策略）、`Comparator<T>` 排序策略。
  - Spring **`InstantiationStrategy`**（Bean 实例化策略）、`Resource` 访问策略。
- **面试官连环追问**：
  1. **直接注入 `Map<String, PayStrategy>` 时，Map 的 Key 是什么？为什么上面代码更推荐注入 `List<PayStrategy>` 再自己转 `Map`？**
     - 直接注入 `Map<String, PayStrategy>` 时，Spring 默认把 **Bean Name（首字母小写类名，如 `alipayStrategy`）** 作为 Key，很容易和业务枚举值（如 `"ALIPAY"`）耦合不一致；注入 `List` 后按自定义 `channel()` 方法收集成不可变 Map 更安全可控，还能在启动时通过 `toMap` 提前发现重复渠道冲突！
- **实战避坑**：
  - 如果不同策略除了算法逻辑差异外还有大量共同的前置参数校验与后置记账日志，务必配合**模板方法模式**抽象一个 `AbstractPayStrategy` 父类，避免每个策略类复制粘贴公共代码。

### Q39：模板方法模式（Template Method）原理及其在 AQS、Servlet、Spring 中的应用？
- **直接结论**：
  - 模板方法模式在抽象父类中定义好算法的**固定骨架流程（通常声明为 `final` 防止子类篡改顺序）**，将其中易变的特定步骤延迟到子类通过重写（Hook 钩子/抽象方法）去实现，是**框架扩展的灵魂模式**。
- **经典框架源码级应用**：
  1. **JDK `AbstractQueuedSynchronizer (AQS)`**：
     - 父类定义好 `acquire(int arg)` 的阻塞入队、自旋、挂起唤醒骨架：`if (!tryAcquire(arg) && acquireQueued(...)) selfInterrupt();`
     - 子类（`ReentrantLock`、`Semaphore`、`CountDownLatch`）只需各自重写 `tryAcquire()` / `tryRelease()` 的 `state` 变更规则即可！
  2. **Servlet `HttpServlet`**：
     - `service()` 方法根据 HTTP Method 分发调用 `doGet()` / `doPost()` / `doPut()` 钩子方法。
  3. **Spring `JdbcTemplate` / `RedisTemplate` / `AbstractApplicationContext.refresh()`**：
     - `JdbcTemplate.execute()` 固定封装获取连接、创建 Statement、异常统一转为 `DataAccessException`、关闭释放连接等繁琐模板代码，仅将 SQL 执行结果提取通过回调接口（`RowMapper` / `StatementCallback`——模板方法与回调的结合）交给调用方。
     - `AbstractApplicationContext.refresh()` 定义了 IoC 容器启动的 12/13 个固定标准步骤，允许子类重写 `onRefresh()`（Spring Boot 正是在此启动嵌入式 Tomcat！）或 `postProcessBeanFactory()`。
- **面试官连环追问**：
  1. **为什么现代框架（如 `JdbcTemplate`）常用“模板方法 + Callback 回调接口”而不是纯靠子类继承重写？**
     - Java 是单继承语言！如果用纯继承模板方法，每次写一条不同的 SQL 都要写一个子类继承 `JdbcTemplate`，类会直接爆炸；结合匿名内部类 / Lambda 回调接口传递差异点，既保留了模板骨架复用，又避免了类膨胀（组合优于继承）。
- **实战避坑**：
  - 设计抽象父类骨架方法（如订单创建主流程 `createOrder()`）时，**务必加上 `final` 关键字**，防止下游业务方图省事直接重写主流程导致风控或事务校验被绕过。

### Q40：观察者模式（Observer）与发布-订阅模式的区别？Spring 事件驱动机制底层原理？
- **直接结论**：
  - **观察者模式**中，观察者与被观察者（Subject）**直接相互感知**（Subject 内部维护观察者列表并直接遍历通知）；**发布-订阅模式（Pub-Sub）**通过中间**事件总线 / 消息代理（EventBus / MQ）**彻底解耦，发布者与订阅者互不知晓对方存在。
- **Spring 事件驱动模型底层原理**：
  - **核心三要素**：
    1. `ApplicationEvent`（事件载体，Spring 4.2+ 后甚至可以直接发布任意 POJO 对象）。
    2. `ApplicationEventPublisher`（发布器，即 `ApplicationContext` 本身）。
    3. `ApplicationListener` / **`@EventListener`**（监听器）。
  - **底层流程**：`publishEvent()` 委托给 **`ApplicationEventMulticaster`（事件广播器，默认 `SimpleApplicationEventMulticaster`）**遍历匹配的监听器执行 `onApplicationEvent()`。
  - **重要特性（同步 vs 异步 & 事务一致性坑）**：
    - Spring 事件**默认是同步执行**的（和发布者在同一个线程、同一个数据库事务内！如果监听器里抛异常会连带回滚主业务）。
    - 加上 **`@Async`** 可开启异步执行（需配合 `@EnableAsync` 配置线程池），但异步后脱离了主事务！
    - 涉及“发短信/推 MQ 必须在数据库事务提交成功之后执行”时，务必使用 **`@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)`**！
- **面试官连环追问**：
  1. **在 `@TransactionalEventListener(AFTER_COMMIT)` 的监听方法里如果再执行一次数据库 `UPDATE` 写入，为什么发现根本没保存进数据库？**
     - 极其经典的 Spring 坑！`AFTER_COMMIT` 回调触发时，原来的事务已经提交结束了，但线程上下文绑定的事务资源可能还没清理彻底，新发起的 DB 操作默认加入不到已提交的事务中导致无法提交。**解决**：在监听方法上显式加上 **`@Transactional(propagation = Propagation.REQUIRES_NEW)`** 开启一个全新独立事务，或者配合 `@Async` 异步处理。
- **实战避坑**：
  - `SimpleApplicationEventMulticaster` 如果配置了全局 `TaskExecutor`，会把**所有** Spring 内部事件全部变成异步，可能导致监听器执行顺序错乱或启动阶段依赖问题；更安全做法是广播器保持默认同步，对需要异步的单个监听器方法单独加 `@Async`。

### Q41：责任链模式（Chain of Responsibility）两种实现变体是什么？在 Servlet、Spring、Netty、MyBatis 中怎么实现的？
- **直接结论**：
  - 责任链模式让多个处理器都有机会处理请求并按链传递。工程中主要有两种变体：**1) 单向线性遍历链**（只往后传或遇拦截终止）；**2) 双向递归/洋葱模型调用链**（请求按 `A -> B -> C` 进入，处理完按 `C -> B -> A` 原路返回收尾）。
- **四大顶级框架源码实现对照**：
  | 框架组件 | 链结构与触发方式 | 核心特性 |
  | :--- | :--- | :--- |
  | **Servlet `FilterChain`** | 递归/索引推进：`ApplicationFilterChain.doFilter()` 内部维护 `pos` 索引，Filter 调 `chain.doFilter(req, resp)` 推进下一个 | 典型的**洋葱模型**：`doFilter` 之前代码按正序执行，之后代码按逆序执行 |
  | **Spring MVC `HandlerInterceptor`** | `HandlerExecutionChain` 数组遍历 | `preHandle()` 正序执行（返回 false 则中断） → Controller → `postHandle()` 逆序 → `afterCompletion()` 逆序（保证资源释放） |
  | **Netty `ChannelPipeline`** | **双向链表**（`HeadContext <-> Handler1 <-> Handler2 <-> TailContext`） | 同时包含 **Inbound（入站，从 Head 向 Tail 传）** 和 **Outbound（出站，从 Tail 向 Head 反向传）**，各自走一条责任链 |
  | **MyBatis `InterceptorChain`** | 层层动态代理包装（`Plugin.wrap(target, this)`） | 拦截四大对象（`Executor`、`StatementHandler`、`ParameterHandler`、`ResultSetHandler`），多插件层层套娃代理 |
- **面试官连环追问**：
  1. **Servlet `Filter` 和 Spring MVC `HandlerInterceptor` 的核心区别是什么？请求进入时谁先执行？**
     - `Filter` 属于 **Servlet 容器规范**（Tomcat），在请求进入 `DispatcherServlet` **之前**执行，无法直接获取 Spring 匹配到的 HandlerMethod 信息，但能篡改原始请求流/响应头；`Interceptor` 属于 **Spring MVC**，在 `DispatcherServlet` 分发之后执行，能拿到具体 `HandlerMethod` 注解信息并依托 Spring IoC 注入 Bean。执行顺序：`Filter(前) -> DispatcherServlet -> Interceptor.preHandle -> Controller -> postHandle -> afterCompletion -> Filter(后)`。
- **实战避坑**：
  - 在 Netty 责任链的 `channelRead()` 中，如果你消费了消息没往下传则无需调用 `ctx.fireChannelRead(msg)`（记得手动 `release`）；如果要继续往下传递则**绝对不能漏掉 `ctx.fireChannelRead(msg)`**，否则下游所有 Handler 都会收不到消息且可能内存泄漏！

### Q42：状态模式（State）与策略模式的区别？在订单状态机中如何实战落地？
- **直接结论**：
  - **状态模式**和**策略模式**的类图几乎相同，但核心区别在于**驱动者与状态流转权**：策略模式中各策略**互相独立平行**，由客户端决定用哪一个；状态模式中各状态**存在严格的前后流转关系**，且状态转换逻辑由状态对象自身或状态机上下文（FSM）内部自动推进，消除业务代码中散落各处的 `if (status == PENDING)` 校验。
- **典型场景与实战落地方案**：
  - **订单状态流转**：`待支付 (WAIT_PAY)` → `已支付 (PAID)` → `已发货 (SHIPPED)` → `已完成 (DONE)` / `已取消 (CANCELED)`。
  - **JDK / 框架源码映射**：Java 线程生命周期 6 大状态（`NEW -> RUNNABLE -> BLOCKED/WAITING -> TERMINATED`）、TCP 连接状态机、**Spring Statemachine** / 阿里开源轻量级无状态状态机 **COLA Statemachine**。
  - **核心落地写法**：定义枚举 `OrderState` + 事件 `OrderEvent` + 状态转换表（`(CurrentState, Event) -> TargetState + Action`）。每次触发事件查表验证是否允许流转，不允许直接报错 `IllegalStateException`，允许则执行动作并 CAS 原子更新数据库状态：`UPDATE t_order SET status = #{target} WHERE id = #{id} AND status = #{current}`。
- **面试官连环追问**：
  1. **并发场景下（比如用户同时点“取消订单”和“发起支付回调”）状态机怎么保证不乱序？**
     - 状态机本身只管状态跃迁规则校验，并发安全必须靠**数据库乐观锁**（`WHERE status = old_status` 判断 `affected_rows == 1`）或 **分布式锁（按 `orderId` 加锁）** 兜底，绝对禁止先查内存判断再无条件 `UPDATE SET status = ...`。
- **实战避坑**：
  - 业务系统慎用重量级的 Spring Statemachine（它内部依赖状态上下文持久化，在高并发无状态微服务里反而显得笨重且容易产生线程安全配置陷阱）；高并发后端首选**“枚举/状态表 + COLA 轻量级状态机 + DB CAS 状态更新”**。

### Q43：命令模式（Command）与迭代器模式（Iterator）原理及在 JDK/Netty 中的应用？
- **直接结论**：
  - **命令模式**将“一个请求/操作”封装成一个独立对象，从而实现请求的**参数化、排队、延迟执行、异步化及撤销重做（Undo/Redo）**；**迭代器模式**提供一种方法顺序访问聚合对象中的各个元素，而又**不暴露其内部底层数据结构**（数组、链表或红黑树）。
- **核心原理与源码映射**：
  1. **命令模式（Command）**：
     - 核心角色：`Command`（命令接口）→ `ConcreteCommand`（持有接收者 Receiver 引用）→ `Invoker`（调用者/任务队列）。
     - **经典源码**：
       - **JDK `Runnable` / `Callable`**：任务本身就是 Command，业务逻辑封装在 `run()` 里，交给 `ThreadPoolExecutor`（Invoker）放入 `BlockingQueue` 排队异步调度执行。
       - **Netty `NioEventLoop` 任务队列**：外部线程通过 `eventLoop.execute(() -> channel.writeAndFlush(msg))` 把写操作封装成 `Runnable` 命令丢进 MPSC 无锁队列，避免多线程并发修改通道状态。
       - **Hystrix `HystrixCommand` / Redis 事务 `MULTI...EXEC` 命令队列**。
  2. **迭代器模式（Iterator）**：
     - **经典源码**：JDK 集合框架 **`Collection.iterator()`**（屏蔽 `ArrayList` 数组、`LinkedList` 双向链表、`TreeSet` 红黑树的遍历差异）、MyBatis `Cursor` 游标。
     - **核心机制 `fail-fast`（快速失败）**：`ArrayList` / `HashMap` 内部维护 `modCount`（结构修改次数），创建迭代器时记录 `expectedModCount = modCount`。如果在 `for-each`（语法糖编译后就是 `Iterator`）遍历过程中直接调用集合的 `list.remove(x)` 而不通过 `iterator.remove()`，就会触发 `modCount != expectedModCount` 并立即抛出 **`ConcurrentModificationException`**（`CopyOnWriteArrayList` 则采用 `fail-safe` 快照遍历，不抛异常但读不到遍历开始后的新修改）。
- **面试官连环追问**：
  1. **为什么在 `for-each` 里只删除倒数第二个元素时，竟然有时候不会抛 `ConcurrentModificationException`？（阿里经典源码坑）**
     - 看 `ArrayList$Itr.hasNext()` 源码：`return cursor != size;`！当删掉倒数第二个元素后，`size` 减 1，此时指针 `cursor` 刚好等于新的 `size`，`hasNext()` 直接返回 `false` 退出了循环，根本没机会调用 `next()` 去检查 `checkForComodification()`，因此神奇地“漏报”了异常——但删除其他位置元素必炸！
- **实战避坑**：
  - 集合边遍历边删除只有三种安全写法：1) `iterator.remove()`；2) JDK 8+ `list.removeIf(predicate)`；3) Stream `filter` 收集新集合。
