## Part 1：简历撰写与项目包装黄金法则

面试官筛选一份简历通常只有 **15~30 秒**。简历不是“工作流水账”，而是**为你接下来的面试设定考纲的广告单**——你写上去的每一个技术词、每一条业务成果，都应该是你提前准备好“连环追问答案”的诱饵。

### 1.1 把 CRUD 业务写成高并发 / 高可用亮点的公式与 6 大实战案例

大多数后端日常开发确实围绕增删改查展开，但同样一个功能，**“流水账写法”** 和 **“工程价值写法”** 在面试官眼中的含金量天差地别。

#### 黄金改写公式
```text
[强动作动词] + [业务痛点 / 数据规模] + [具体技术手段 / 架构方案] + [可量化的性能 / 稳定性 / 业务收益]
```

- **强动作动词库**：主导、设计、重构、落地、治理、排查解决、压测调优、抽离封装（避免全篇“负责、参与、协助、使用”）。
- **可量化指标库**（没有高 QPS 时照样能写出彩）：
  - **耗时类**：接口 P99 耗时从 `480ms` 降至 `65ms`（降低 86%）；跑批时长从 `3.5 小时` 缩短至 `22 分钟`；
  - **资源类**：SQL 扫描行数从 `120 万` 降至 `50 行内`；JVM 单次导出峰值内存从 `2.4GB` 降至 `120MB`；MySQL CPU 负载下降 `65%`；
  - **稳定性类**：核心链路缓存命中率达 `99.2%`；线上死锁/超卖报错清零；故障发现与止血 MTTR 缩短至 `3 分钟`。

### 1.3 简历投递前自查：10 大致命雷区

1. **到处写“精通”**：写“精通 JVM / 精通 Spring / 精通 MySQL”，相当于向资深架构师发起挑战，一追问源码细节立刻挂掉。建议统一用 **“深入理解 / 熟练掌握 / 熟悉 / 了解”** 四个梯度。

4. **技术栈前后自相矛盾**：前面写 `Spring Boot 1.5 + JDK 8`，后面写“利用 JDK 21 虚拟线程提升 5 倍吞吐量”。
5. **工作时间线无解释断层或重叠**：空窗期超过 3 个月无任何交代，或两段工作时间重叠，背调极易翻车。
6. **技术名词大小写错乱、排版不规范**：把 `MySQL` 写成 `Mysql`、`Spring Boot` 写成 `springboot`、`Redis` 写成 `redis`、`Nginx` 写成 `Ngnix`——细节反映工程规范意识。
7. **通篇“参与了”分不清个人贡献**：写“参与了电商系统开发”，面试官分不清核心链路是不是你写的。自己主导的必须明确写 **“主导设计 / 独立开发 / 重构优化”**。
8. **忽视可观测性与工程化交付**：只谈功能实现，不提日志链路追踪（TraceId）、监控告警（Prometheus/Grafana）、压测（JMeter）、代码规范与单测。

10. **盲目塞入自己没跑通的热点词**：听说 AI/K8s 火就硬写上简历，结果连 MCP/RAG 流程或 Pod CrashLoopBackOff 都答不上来——**简历上的任何词被问住两次，往往直接判定“简历注水”**。

## Part 2：面试官项目深挖 15 连问及 STAR+R 法则高分应答模板

项目深挖通常占一面、二面 **40%~60%** 的时间。面试官通过连续追问，核心验证两件事：
1. **真实性**：这个项目到底是不是你亲手做的，还是背别人的总结？
2. **工程思维**：面对业务约束、性能瓶颈与线上风险时，你是否具备 **Trade-off（权衡取舍）** 与 **闭环复盘** 能力？

### 2.1 STAR+R 进阶应答框架

```text
S (Situation)  : 15 秒交代业务背景、数据体量、核心痛点（切忌冗长讲业务名词）
T (Task)       : 明确你的核心指标与约束条件（如：零停机、预算有限、不能超卖）
A (Action)     : ★重点★ 为什么选方案 A 不选方案 B？关键参数怎么定？兜底防线是什么？
R (Result)     : 可量化的技术与业务结果（RT、QPS、CPU、报错率、成本节省）
R (Reflection) : 事后复盘——当前方案的局限性是什么？如果流量再翻 10 倍怎么演进？
```

### 2.2 场景一：性能调优类（Q1 ~ Q3）

#### Q1：你说把核心接口耗时从 500ms 降到了 50ms，具体怎么一步步定位瓶颈的？
- **考察意图**：是否真做过性能剖析，还是拍脑袋乱猜加缓存。
- **❌ 扣分回答**：“我觉得可能是数据库慢，就加了个索引和 Redis 缓存，然后就快了。”
- **✅ STAR+R 高分模板**：
  - **S/T**：大促前商品详情聚合接口 P99 耗时高达 480ms，目标在不加机器的前提下压到 80ms 以内。
  - **A（定位手段）**：先通过 **SkyWalking 链路追踪** 拆解各 Span 耗时，并在预发用 **Arthas `trace`** 命令对方法内部逐行打点，发现 480ms 分布在三块：
    1. 串行调用 3 个下游 RPC 接口（用户等级、促销标签、库存状态）占 **320ms**；
    2. 一条带多表 `JOIN` 的规格查询 SQL 未走覆盖索引占 **140ms**；
    3. 大对象 JSON 序列化和框架开销占 **20~40ms**。
  - **A（优化动作）**：
    1. 将无强依赖的 3 个 RPC 改为 `CompletableFuture` + 独立业务线程池并行拉取，耗时降为最慢接口的 **105ms**；
    2. 对高频静态配置引入 **Caffeine 本地缓存（30s TTL）**，命中直接免去 RPC；
    3. 拆分大 `JOIN`，重建联合索引实现 **覆盖索引** 消除回表，SQL 耗时降至 **8ms**。
  - **R**：最终压测 P99 稳定在 **45ms** 左右，接口吞吐提升 4 倍以上。

#### Q2：用 `CompletableFuture` 并行调用，线程池参数怎么定的？上下文（TraceId/用户态）丢失怎么解决？
- **考察意图**：并发工程细节与常见生产踩坑意识。
- **✅ 高分回答要点**：
  1. **为什么不直接用默认池**：`CompletableFuture.supplyAsync()` 默认使用全局共享的 `ForkJoinPool.commonPool()`，一旦里面有慢 IO 任务会把整个应用其他并行流全部拖死，因此必须**按业务域隔离自定义线程池**。
  2. **参数设定依据**：下游主要是 RPC 和 DB 属于 **IO 密集型**。以 8 核容器为例，结合单机压测拐点将核心线程数设为 32、最大 64，使用容量 200 的 `ArrayBlockingQueue` **有界队列**防止内存溢出，拒绝策略采用 `CallerRunsPolicy`（由 Tomcat 工作线程同步兜底执行，天然反压降速而不直接丢请求）。
  3. **上下文透传坑**：由于线程池复用线程，`InheritableThreadLocal` 只在创建线程时拷贝一次，复用后就会读到脏上下文或丢失 TraceId。我们统一引入阿里 **`TransmittableThreadLocal (TTL)`** 并用 `TtlExecutors.getTtlExecutorService()` 装饰线程池，保证 TraceId 与用户态无损传递。
- **🔥 延伸追问**：`CompletableFuture.allOf()` 如果其中一个非核心任务超时 5 秒，会阻塞整个接口吗？
  - *点拨*：不会，必须在 `get(timeout, TimeUnit.MILLISECONDS)` 或 JDK 9+ 的 `orTimeout()` / `completeOnTimeout(defaultValue, ...)` 设置严格单步超时与降级默认值！

#### Q3：上线后你怎么验证优化真的生效且没有引入数据不一致或资源打满？
- **考察意图**：工程闭环与灰度发布素养。
- **✅ 高分回答要点**：
  1. **压测验证**：预发环境使用 JMeter 按线上峰值 2 倍流量压测 30 分钟，重点观察 P99 曲线、Young GC 频率、线程池队列堆积量及 DB 连接池 `active` 数。
  2. **灰度对比**：生产环境先放 **10% 灰度流量**，在 Grafana 面板实时对比新老版本实例的 TP99 与 5xx 报错率。
  3. **数据校验**：针对新加的本地/Redis 缓存，上线初期挂了 48 小时**旁路异步比对日志**（按 1% 抽样对比缓存结果与 DB 实时查询结果），确认一致率 100% 后再全量推开。

### 2.3 场景二：线上故障排查类（Q4 ~ Q6）

#### Q4：聊一个你印象最深的线上故障，当时怎么发现和止血的？
- **考察意图**：线上救火能力、稳定性优先意识。
- **❌ 扣分回答**：“有次上线我忘了判断对象为空，报了空指针异常，后来加了个 `if (x != null)` 就好了。”
- **✅ 高分策略**：讲一个涉及 **JVM 内存泄漏 / CPU 正则回溯 / MySQL 死锁 / Redis 整点雪崩 / MQ 百万积压** 的真实排查故事，严格按照 **“先止血保业务 → 保留现场 → 工具定位根因 → 修复闭环”** 四步讲述（完整剧本直接套用 **Part 3**）。

#### Q5：为什么测试环境没测出来，一上生产就爆了？
- **考察意图**：理解生产环境与测试环境的本质差异。
- **✅ 高分回答要点（三大本质差异）**：
  1. **数据量级与分布差异**：测试库只有几千行数据，全表扫描不到 10ms；生产几千万行才暴露索引选择退化（如区分度低不走索引）或长事务锁等待。
  2. **并发度与时序竞态**：测试环境多为单人手工点测，难以触发高并发下的热点行锁争抢、数据库连接池打满或缓存击穿瞬时并发。
  3. **异常流量与外部依赖抖动**：生产环境存在爬虫恶意参数（如超长字符串触发正则回溯、超大 `pageNum=100000` 深分页）以及三方网关偶发网络抖动超时。

#### Q6：故障解决后，你们团队沉淀了哪些“机制性防复发”措施？
- **考察意图**：区分“修 Bug 的码农”与“建体系的高级工程师”。
- **✅ 高分回答要点（三道防线）**：
  1. **事前研发卡点**：CI 流水线集成 SonarQube 静态规则扫描（拦截无界集合、未关闭流、未设超时 HTTP 客户端）与 SQL 审核平台拦截无索引大查询。
  2. **事中可观测告警**：补充细粒度监控告警——线程池队列使用率 > 70%、接口慢调用比例、MySQL 死锁数、Old Gen 使用率 > 85% 全部接入秒级飞书/钉钉群报警。
  3. **事后混沌演练**：将本次故障抽象为标准测试用例，每季度在预发/线上低峰期做一次强弱依赖降级与故障注入演练，确保熔断开关长期有效。

### 2.4 场景三：技术选型与架构权衡类（Q7 ~ Q9）

#### Q7：扣库存为什么要用 Redis + Lua，而不是直接用 MySQL 悲观锁/乐观锁？
- **考察意图**：高并发架构下的性能瓶颈认知与一致性权衡。
- **✅ 高分回答要点**：
  1. **对比分析**：直接用 MySQL 单行更新（`UPDATE stock SET num = num - 1 WHERE sku_id = ? AND num >= 1`）在常规低并发场景最稳妥、强一致且代码最简单。但在秒杀大促场景下，上万请求同时竞争同一热门 `sku_id`，InnoDB 行锁排队会导致大量线程阻塞，数据库连接池瞬间耗尽，单库极限吞吐也就几百到一千 TPS。
  2. **方案收益与代价（Trade-off）**：将库存预热至 Redis，利用单线程模型 + Lua 脚本保证“查库存 + 扣减 + 记用户购买标”的原子性，单分片即可扛住上万 QPS，再发 MQ 异步建单落库。**代价**是引入了缓存与 DB 的最终一致性复杂度，我们通过 MQ 消费失败重试、超时关单自动回补库存以及 T+1 定时对账任务来兜底。

#### Q8：消息队列为什么选 RocketMQ，而不是 Kafka 或 RabbitMQ？
- **考察意图**：是否真正对比过中间件底层特性与业务匹配度。
- **✅ 高分回答要点**：
  - 结合核心交易诉求对比四大维度：
    1. **功能特性**：交易履约强依赖 **半事务消息**（保证本地 DB 与发 MQ 原子性）和 **多级延迟消息**（15 分钟未支付自动关单），RocketMQ 原生完美支持；Kafka 更侧重海量日志吞吐与流式采集，原生不支持多级定时延迟；RabbitMQ 延迟依赖死信队列或插件。
    2. **海量堆积能力**：RabbitMQ 队列积压过多引发内存换页时吞吐会断崖下跌；RocketMQ 与 Kafka 基于磁盘顺序写，支持千万级以上堆积不降速。
    3. **团队技术栈可控性**：RocketMQ 为纯 Java 源码，团队遇到极端 Bug 能直接看源码排查或定制改造，运维排错门槛低于 Erlang 栈的 RabbitMQ。

#### Q9：分布式事务为什么不用 Seata AT/TCC 全家桶，而用本地消息表 / 事务消息？
- **考察意图**：避免盲目堆砌重量级框架，考察性能与复杂度的取舍。
- **✅ 高分回答要点**：
  1. **性能与侵入性评估**：Seata AT 模式依赖全局锁和 Undo Log 解析，高并发热点行场景下全局锁竞争会严重拉低系统吞吐；TCC 模式虽然无全局锁、性能好，但开发成本极高，每个接口都要写 Try/Confirm/Cancel 三套逻辑，还要自己防**空回滚、防悬挂和幂等**。
  2. **分级治理策略**：我们把 95% 可异步化的跨服务联动（如送积分、核销优惠券、发通知、同步物流单）全部采用 **RocketMQ 事务消息 / 本地消息表 + 消费端幂等 + 定时补偿** 实现最终一致性；只有极少数必须同步强一致扣减的核心账务链路，才谨慎评估 TCC。

### 2.5 场景四：分库分表与架构重构类（Q10 ~ Q12）

#### Q10：你们单表到多少数据量开始分库分表的？为什么不用分区表或直接上 TiDB？
- **考察意图**：拒绝教条主义（死背“2000万行”），看真实容量评估能力。
- **✅ 高分回答要点**：
  - 我们不机械卡“2000 万行”红线，而是看 **单行字节宽 × 行数、B+ 树高度、Buffer Pool 命中率与 DDL 风险**。
  - 当时订单单行约 1.5KB，4500 万行时表物理体积逼近 80GB，索引体积超出服务器可用内存一半，Buffer Pool 频繁换页导致 IOPS 飙升，且主库单机写入接近瓶颈、在线加字段 DDL 风险极高。
  - **为什么不选分区表**：分区表本质仍在同一个 MySQL 实例上共享 CPU、磁盘 IO 与连接池，解决不了单库写入上限问题；
  - **为什么不直接迁 TiDB**：当时团队缺乏 NewSQL 分布式集群运维经验且硬件成本翻倍，因此选用最稳妥的 **ShardingSphere 8 库 64 表**，配合 1 年前冷数据定期归档策略。

#### Q11：分库分表后，按非分片键查询、多条件分页、跨库 JOIN 怎么解决？
- **考察意图**：分库分表核心痛点实战落地。
- **✅ 高分回答要点**：
  1. **基因法解决双维度精准路由**：生成 `order_id` 时将 `user_id % 64` 的基因位嵌入订单号末尾，这样无论 C 端用户按 `user_id` 查列表还是按 `order_id` 查详情，都能直接计算出同一分片，**零跨库广播**。
  2. **异构索引（Canal + ES）解决后台多维检索**：商家和运营后台按时间范围、商品名称、订单状态多条件分页查询，全部通过 **Canal 订阅 MySQL Binlog 拼装宽表实时同步进 Elasticsearch**，ES 承担复杂搜索及 `search_after` 深分页，点击查看强一致详情时再拿主键回查分库。

#### Q12：千万级大表迁移到分库分表，如何保障不停机、不丢数据、随时可回滚？
- **考察意图**：大型数据架构迁移的风险控制细节。
- **✅ 五步零停机平滑迁移方案**：
  1. **双写阶段**：改造业务层（或利用 Canal 异步同步），新数据写老库的同时双写新分库（此时老库为主、新库失败不阻断主流程但记告警重试）。
  2. **历史全量 + 增量追平**：用 DataX 迁移历史存量数据，再用 Canal 追平迁移窗口期的增量并按 `update_time` 幂等覆盖。
  3. **多轮自动化核对**：编写校验脚本抽样及全量比对老库与新分库的总行数及核心字段（金额/状态）MD5，连续跑平零差异。
  4. **灰度切读**：按用户尾号 5% → 20% → 100% 切到新分库读取（老库随时可作为开关兜底回切）。
  5. **切主保留回滚窗**：切换为“以新库为主写、反向异步同步老库”运行 1~2 周，确认毫无异常后再下线老库写入。

### 2.6 场景五：高并发压测与容灾演练类（Q13 ~ Q15）

#### Q13：线上全链路压测怎么隔离数据，确保不会污染真实账务、库存和用户消息？
- **考察意图**：大型工程压测的实操经验。
- **✅ 高分回答要点（全链路染色 + 透明隔离）**：
  1. **流量染色与透传**：压测工具在入口注入 HTTP Header `X-Stress-Test: true`，经过网关、OpenFeign 拦截器、`TransmittableThreadLocal` 以及 MQ Message Property 贯穿整个微服务调用链。
  2. **存储与外部依赖隔离**：
     - **MySQL**：JDBC / ShardingSphere 拦截器识别到压测标记后，自动改写路由到预置的**影子库或影子表（如 `t_order_shadow`）**；
     - **Redis**：RedisSerializer / 切面自动拼接 `_stress` Key 前缀并设置较短 TTL；
     - **MQ**：生产者自动发往影子 Topic，消费端独立隔离消费；
     - **外部三方网关**（微信/支付宝扣款、短信发送、顺丰下单）：在网关或客户端层接入 **Mock 挡板**，直接返回预设成功响应与标准耗时，保证 100% 贴近真实链路且零脏数据。

#### Q14：接口限流阈值怎么定？突增流量超过阈值后用户体验怎么保？
- **考察意图**：容量规划与优雅降级意识。
- **✅ 高分回答要点**：
  1. **单机阶梯压测找拐点**：绝对不是拍脑袋定的。比如 4C8G 节点压测到 600 QPS 时 CPU 68%、P99 40ms；到达 750 QPS 后线程池队列堆积、RT 骤升至 500ms+，于是单机安全水位定为 500 QPS，4 台集群总阈值设为 2000 QPS。
  2. **平滑防护与兜底体验**：结合 Sentinel 的 **Warm Up 预热模式**防止冷启动突发打死，并配合系统自适应规则（Load/CPU 兜底）。超阈值触发限流后，返回预设的友好提示或静态兜底缓存页，绝不直接抛 HTTP 500 白页。

#### Q15：如果 Redis 集群突然整体不可用，核心交易系统会直接瘫痪吗？
- **考察意图**：单点/中间件故障下的容灾降级思维。
- **✅ 高分回答要点**：
  - 不会整体雪崩，我们按接口级别做了**分级降级开关**：
    1. **高频读接口**：进程内有 **Caffeine 本地二级缓存**兜底，Redis 挂掉时本地缓存能拦截掉绝大部分重复读，且回源 DB 加了本地 `Semaphore` 并发信号量限流保护数据库不被打死；
    2. **分布式锁与限流校验**：通过配置中心热开关切换为 **数据库唯一索引防重 + 乐观锁兜底校验**模式，宁可局部吞吐降低，也绝不出现超卖或资金错账，保证核心下单依然可用。

### 3.2 六大经典生产事故标准讲述剧本与关键代码/命令

#### 事故 1：CPU 飙升 100%，服务全部超时

- **1. 现象与紧急止血**：
  大促预热期间，监控告警某节点 CPU 瞬时打满 100%，网关大量报 504 Timeout。我们第一时间在 Nacos / 负载均衡摘除该异常节点流量（**保留现场不直接 kill -9**），其余节点承接流量，业务 1 分钟内恢复。
- **2. 现场排查命令链**：
  ```bash
  # 1. 找到 CPU 最高的 Java 进程 PID
  top -c
  # 2. 查看该进程下 CPU 飙高的线程 TID（假设 PID=12345）
  top -Hp 12345
  # 3. 将最忙的线程 TID（如 12388）转为 16 进制 -> 0x3064
  printf "%x\n" 12388
  # 4. 导出线程栈精准定位代码行（或者直接用 Arthas 一键查看：thread -n 3）
  jstack 12345 | grep 0x3064 -A 30
  ```
- **3. 根因揭晓（二选一适配自身项目）**：
  - *分支 A（正则灾难性回溯）*：`jstack` 显示工作线程全部卡在 `java.util.regex.Pattern$Branch.match()`。排查发现用户输入了超长嵌套特殊字符，触发有缺陷正则的指数级回溯，把所有工作线程 CPU 榨干。
  - *分支 B（频繁 Full GC）*：`jstack` 占用 CPU 全是 `GC Thread#0..7`，结合 `jstat -gcutil 12345 1000` 看到 `O`（老年代）达 99.9% 且 `FGC` 每秒狂涨，GC 线程空转吃满 CPU。
- **4. 修复与防复发**：重构正则消除嵌套量词（或改用线性时间复杂度的 Google RE2J 引擎）并对超长输入做长度拦截；配置老年代使用率 > 85% 提前预警。

---

#### 事故 2：内存泄漏导致频繁 Full GC 与 `OutOfMemoryError`

- **1. 现象与紧急止血**：
  报表导出服务上线 48 小时后在每天下午高峰必发 OOM 重启，日志抛出 `java.lang.OutOfMemoryError: Java heap space`。因为我们提前在 JVM 启动参数配好了 `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/logs/heap.hprof`，OOM 时自动保留了堆转储现场，我们先临时扩容 2 台实例并做滚动重启维持可用。
- **2. 排查定位**：
  将 `heap.hprof` 导入 **Eclipse MAT**，打开 **Leak Suspects（泄漏疑点）** 与 **Dominator Tree（支配树）**，发现 `byte[]` 和业务缓存对象占用了 85% 堆空间，顺着 **Merge Shortest Paths to GC Roots** 追溯到典型元凶：
  - *元凶 A（无界本地缓存）*：同事用全局 `static Map` 存用户临时数据，既无容量上限也无过期淘汰。
  - *元凶 B（ThreadLocal 未清理）*：线程池线程复用下，拦截器写入 `ThreadLocal` 的上下文大对象遇到异常未执行 `remove()`，随核心线程永久存活。
- **3. 防坑修复代码示范**：
  ```java
  // ❌ 错误：业务抛异常或提前 return 时跳过 remove()，线程池下必然内存泄漏
  UserContextHolder.set(largeContext);
  doBusiness();
  UserContextHolder.remove();

  // ✅ 正确：强制 try-finally 清理；本地缓存统一使用 Caffeine 配置上限与 TTL
  try {
      UserContextHolder.set(largeContext);
      doBusiness();
  } finally {
      UserContextHolder.remove();
  }
  ```

---

#### 事故 3：下游慢调用引发服务雪崩（级联超时）

- **1. 现象与紧急止血**：
  第三方风控接口网络抖动，响应时间从 30ms 恶化到 8s。短短 3 分钟内，我们核心下单服务连带不需要风控的查询接口全部报错 503。
- **2. 排查定位**：
  1. 查看 SkyWalking 链路追踪发现大量请求长时间卡在风控 HTTP 调用上；
  2. 通过 `jstack` / Arthas `thread` 发现 Tomcat 的 **200 个工作线程几乎全部处于 `RUNNABLE`（阻塞在 `SocketInputStream.socketRead0`）**；
  3. 检查源码发现调用风控用的 `RestTemplate`/`OkHttp` **未显式配置 `readTimeout`**（默认无限或设成了 30s），且非核心外部调用与核心接口共用 Tomcat 工作线程池。
- **3. 止血与长期防复发**：
  - **止血**：立即通过配置中心打开降级开关，对白名单/低风险用户跳过外部强风控放行，Tomcat 线程瞬间释放。
  - **防复发**：所有 HTTP/RPC 客户端强制配置严格超时（`connectTimeout=500ms, readTimeout=1500ms`）；引入 **Sentinel 慢调用比例熔断 + 舱壁线程池隔离** 彻底阻断级联雪崩。

#### 事故 4：并发批量更新触发 MySQL 死锁（Deadlock found）

- **1. 现象与紧急止血**：
  大促购物车并发下单扣减多件商品库存时，日志频发 `Deadlock found when trying to get lock; try restarting transaction`。
- **2. 排查定位**：
  登录 MySQL 执行 `SHOW ENGINE INNODB STATUS\G` 查看 `LATEST DETECTED DEADLOCK` 段落：
  - 看到 **Transaction (1)** 持有 `sku_id=101` 的 X 锁并等待 `102` 的 X 锁；
  - **Transaction (2)** 持有 `102` 的 X 锁并等待 `101` 的 X 锁，形成典型环路等待（或两事务同时 `SELECT ... FOR UPDATE` 不存在记录拿到间隙锁后互相 `INSERT` 等待插入意向锁）。
- **3. 根因修复代码示范**：
  ```java
  // ✅ 破除环路等待：进入数据库事务更新库存前，统一按 skuId 升序排列！
  List<OrderItem> sortedItems = items.stream()
      .sorted(Comparator.comparing(OrderItem::getSkuId))
      .toList();
  ```
  同时将事务内无关的 RPC/MQ/日志操作全部移出事务外缩短持锁时间；对不存在记录的防重改用数据库唯一索引 + `INSERT IGNORE` 替代先查后插的间隙锁冲突。

#### 事故 5：Redis 热点 Key 击穿与整点缓存雪崩

- **1. 现象与紧急止血**：
  整点秒杀开启后 1 小时，提前预热的优惠券配置同一秒集体过期，上万请求瞬间击穿到 MySQL，数据库连接池打满 100% 飙升报警。
- **2. 排查定位**：
  通过 Redis 监控 `keyspace_misses` 曲线发现命中率在整点断崖下跌，同时 MySQL `Threads_running` 暴涨到上千，全在执行同一条优惠券配置查询 SQL。
- **3. 止血与长期防复发三板斧**：
  - **止血**：立即在网关与核心接口开启**本地内存兜底降级开关**，拦截回源 DB 的洪峰流量。
  - **防复发**：
    1. **打散过期时间**：基础 TTL 叠加随机抖动（`3600 + ThreadLocalRandom.current().nextInt(600)`）；
    2. **热点 Key 逻辑过期 + 互斥锁重建**：核心配置永不物理过期，Value 内嵌 `expireTime`，过期后仅放行 1 个拿到分布式锁的线程异步更新；
    3. **Caffeine 本地二级缓存**：即使 Redis 分片抖动或热点打满网卡，本地缓存依然拦截 95%+ 重复读请求。

#### 事故 6：RocketMQ / Kafka 百万级消息积压紧急消峰

- **1. 现象与紧急止血**：
  监控告警订单通知 Topic 积压超过 **300 万条消息**，用户支付后迟迟收不到推送通知。
- **2. 排查定位**：
  登录 RocketMQ Dashboard 看到所有 Consumer 在线，但消费 TPS 从平时的 2000 暴跌到 25。拉取消费线程栈发现消费逻辑里同步调用了一个出现故障的第三方短信网关（每次卡死 10 秒超时）。
- **3. 紧急消峰四步杀手锏**：
  1. **修复/降级消费逻辑阻塞点**：先降级跳过故障三方网关或修复 Bug，恢复单条消费正常耗时；
  2. **核查 Queue/Partition 数量**：如果原 Topic 只有 4 个 Queue，你把 Consumer 扩容到 20 台也没用，16 台会空转（一个 Queue 同一时刻只能被同组一个 Consumer 消费）！
  3. **临时新建大分区 Topic 极速转发**：新建一个拥有 **32 个 Queue 的临时 Topic**，上线轻量级“纯转发消费者”（不做任何 DB/RPC，每秒转发数万条）将原积压消息快速搬运到新 Topic，再拉起 32 台临时消费节点并发狂飙消费！
  4. **事后收尾**：积压清零后下线临时转发程序和多余实例，并补充积压梯度告警（> 5 万警告，> 20 万电话告警）。

  - *暂无 Offer 时*：“我近期刚正式启动机会对比，目前投递的几家集中在初复试阶段，还没有到最终 Offer 环节，贵司是我非常看重的目标平台之一。”

#### 10. 校招专项高频：实习转正意愿 / 挂科或跨专业 / 为什么不读博或考公？
- **校招模板**：突出自己对工程落地和创造商业价值的成就感（如“相比偏理论的学术研究，我更喜欢写出的代码能直接服务千万用户、能实时看到 QPS 和性能提升带来的正反馈”）；若有挂科如实承认当时时间管理失误并展示后续高分课程或开源/竞赛成果证明学习能力已大幅提升。

### 4.2 期望薪资、总包拆解与谈薪实战话术（多拿 10%~30%）

1. **永远算清“年总包（Total Package）”而不是只看月薪 Base**：
   ```text
   总包价值 = 基本月薪(Base) × 保底月数(12/13/14薪)
            + 绩效/年终奖(问清历史平均发放系数及是否写入合同)
            + 签字费(Sign-on Bonus，可用来弥补跳槽损失的年终奖)
            + 股票/期权(注意归属周期 4 年与上市变现难度，未上市谨慎估值)
            + 隐性福利(公积金 5% vs 12% 每月现金差额巨大！另有房补/餐补/加班费)
   ```
2. **HR 问期望薪资时，绝不轻易自报过低底价**：
   - *标准话术*：“我目前年包大概在 X 万左右，考虑到这次跳槽承担的模块复杂度与职责提升，期望总包能在 **20%~30% 的合理涨幅区间**（大约 A~B 万）。不过我对贵司平台和团队非常认可，具体也可以结合贵司对我的技术定级与薪酬带宽来沟通。”
3. **谈薪核心铁律**：
   - 给 HR **确定性承诺**（“只要能申到 XX，我立刻签字”）比漫天要价有效 10 倍；
   - 如果 Base 确实卡死在定级上限，可以尝试争取 **Sign-on 签字费** 或 **股票/期权加码**，HR 通常更容易批一次性奖金。

## Part 5：面试结尾“反问面试官”高情商清单（附团队避坑信号）

面试官最后问：“你还有什么想问我的吗？”——**千万不要回答“没有了，我挺清楚的”！** 没有问题往往显得缺乏思考深度与求职主动性。

| 面试轮次 | 面试官角色 | 高情商必问清单（每轮挑 1~2 个） | 反问后的“团队排雷观察信号” |
| :--- | :--- | :--- | :--- |
| **一面** | 技术骨干 / 未来同事 | 1. “想请教咱们目前核心业务的主力技术栈是什么？近期在系统性能或架构上有没有重点攻坚的痛点？”<br>2. “团队日常的工程实践是怎样的？比如 Code Review、自动化测试覆盖率和 CI/CD 发布流程？”<br>3. “刚才的交流中，您觉得我在哪些技术细节或思考维度上还有提升空间？” | ⚠️ **避坑信号**：如果对方支支吾吾说“没有 Code Review、直接手动打 Jar 包丢服务器、全靠人肉改线上数据库”，说明工程规范极差、技术债深重。 |
| **二/三面** | 架构师 / Team Leader / 总监 | 1. “如果我有幸加入，**前 3 个月到半年最希望我重点解决什么核心问题**，或者达成什么样的交付目标？”（极佳的主人翁意识加分项）<br>2. “未来 1~2 年，咱们这条业务线在架构演进或流量规模上最大的挑战是什么？”<br>3. “作为团队负责人，您最看重后端工程师身上哪两项核心特质？” | ⚠️ **避坑信号**：如果 Leader 连未来 3 个月岗位目标都说不清，只反复强调“来了就是配合业务写需求、需要能抗住经常熬夜救火”，大概率是纯工具人救火坑位。 |
| **HR 面** | HRBP / 招聘经理 | 1. “想了解咱们公司的绩效考核周期、晋升评估窗口和标准是怎样的？”<br>2. “新员工入职后是否有 Mentor 导师带教或系统化的业务培训体系？”<br>3. “咱们后续的定级审批与 Offer 流程大约需要几个工作日？” | ⚠️ **避坑信号**：含糊回避五险一金缴纳基数（按最低基数而非全额工资）、把试用期拉满 6 个月且试用期薪资打 8 折、年终奖全靠口头画饼不写进任何条款。 |

> **禁忌提醒**：一面技术面**绝对不要**一上来就问“双休吗、有加班费吗、年终奖发几个月”——这类问题统一留在 HR 终面谈薪阶段再优雅核实。

### 6.2 7 天极速冲刺计划（适合已约好下周面试救急）

- **Day 1（简历定位与开场）**：对照 Part 1 紧急检查简历红线；打磨 90 秒完美自我介绍；口头理顺 2 个核心项目的系统架构图与数据流向。
- **Day 2（Java 核心 + 并发 + JVM 突击）**：速过 `HashMap` 1.8、线程状态与线程池 7 参数、`volatile`/`synchronized`/AQS、G1 原理及 `top`+`jstack`+`jmap` 排查流程。
- **Day 3（MySQL + Redis 必考硬骨头）**：死磕 B+ 树索引下推/覆盖索引/优化、MVCC、临键锁与死锁；Redis 底层编码、集群脑裂、雪崩/击穿/穿透、Redisson 看门狗机制。
- **Day 4（Spring + MQ + 微服务核心）**：IoC/循环依赖三级缓存、`@Transactional` 7 大失效场景；RocketMQ/Kafka 消息不丢失/幂等/积压；Seata/Nacos/Sentinel 原理。
- **Day 5（高频手撕算法 Top 20 + SQL 手写）**：集中敲一遍必考原题（反转链表、LRU Cache、K 个一组翻转链表、快排/归并、二叉树层序/最近公共祖先、岛屿数量、三数之和）及窗口函数 TopN SQL。
- **Day 6（项目深挖 15 连问 + 故障剧本彩排）**：结合 Part 2 和 Part 3，对着手机录音完整讲述 2 个项目和 2 个线上事故（严格控制在每题 2~3 分钟内，逻辑清晰不啰嗦）。
- **Day 7（错题复盘与心态调整）**：轻量回顾易忘参数与 Part 5 反问清单，早睡保证精力充沛——**考前最后一天切忌再硬啃全新生僻框架，确保已会的高频题答得稳、答得深！**

### 6.3 面试前 24 小时与手撕代码临场自检 Checklist

- [ ] **简历“零盲区”核验**：自己发给 HR 的 PDF 版简历中，**每一个标黑的技术关键词**都能张口说出“是什么 + 为什么这么选 + 踩过什么坑”。
- [ ] **手撕代码临场沟通法则**（遇到卡壳时千万别沉默干坐着 5 分钟！）：
  - [ ] 先口头确认边界条件（空数组、负数、重复元素、数据范围与时间/空间复杂度目标）；
  - [ ] 先讲暴力解思路保底，再逐步优化（如“暴力是 $O(n^2)$，我可以用哈希表或双指针优化到 $O(n)$”），面试官通常会在你开口思考时主动给提示；
  - [ ] 写完代码主动带入 **2 组正常/边界测试用例（如 `null`、单节点）** 口头 Dry Run 一遍再交卷。
- [ ] **线上面试硬件环境检查**：测试麦克风与耳机防回音、关闭微信/系统弹窗通知、准备好可共享屏幕的干净浏览器/IDE、备好一张白纸和笔用于画架构图推演。
- [ ] **面试后 30 分钟黄金复盘**：无论发挥好坏，结束半小时内记录所有被问到的真题和卡壳点，当晚补充进错题本——**把每一场面试都变成下一场必拿 Offer 的垫脚石！**
